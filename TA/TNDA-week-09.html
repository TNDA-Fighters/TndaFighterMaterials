課前實作練習 1｜StateTree 導讀的三題開放問答

細步驟解答

三題沒有唯一答案。助教要確認學生能用例子說明理由，不只背名詞。 以下是參考方向，不要求學生採用同一種設計。

第 1 題：你會怎麼切狀態？

  • 參考例子：把敵人分成「追逐」與「休息」兩個 State。追逐中，移動 Task 負責靠近玩家，Delay Task 同時計時；時間到再轉入休息。兩個 Task 可以同時工作，不必各拆成一個 State。
  • 判讀重點：學生能說清楚每個 State 代表什麼行為、Task 做什麼、何時切換狀態，並解釋自己的拆分理由。採用巡邏、警戒或其他遊戲案例也可以。
  • 可以追問：「如果把這兩個 Task 拆成兩個先後執行的 State，角色行為會有什麼不同？」看學生是否理解同時執行與先後執行的差別。

第 2 題：你會從哪裡查起？

  • 提早切到 Rest：先看 Chase 的完成規則與 Transition。例如 Tasks Completion 是 Any，而移動 Task 比 Delay 先完成，就可能觸發 On State Completed，讓樹在 1.2 秒前切到 Rest。也要檢查是否有其他 Transition 提早切換。
  • 時間到卻仍在 Chase：若完成規則是 All，移動 Task 又一直 Running，Delay 完成後仍可能等不到整個 State 完成。要一起核對 Any／All、各 Task 的 Considered for Completion，以及轉移的觸發條件。
  • 判讀重點：學生要提出一次只改一個設定的小實驗，並預測結果。例如只調整移動 Task 是否參與完成判定，再看切換時間是否改變。不能只回答「全部改成 All」卻說不出原因。

第 3 題：你會把判斷放哪裡？

  • 參考分工：Evaluator 更新與玩家的距離；Condition 判斷是否超過門檻；Transition 決定是否切到其他 State；Task 執行追逐或停止追逐的動作。
  • 判讀重點：繼續追、停下或改做別的事都可以，但學生要說明資料由誰提供、在哪裡判斷、如何觸發切換，以及玩家會感受到什麼。
  • 可以追問：「你把距離條件放在 Enter Condition，角色進入 Chase 後，靠什麼觸發重新選擇？」確認學生知道 Enter Condition 篩選進入資格，不會單靠條件變化就自動切走。

每題最後請學生指出一個仍不理解的地方，以及對應的導讀章節或影片時間點，助教再針對該處補講。

課前實作練習 2｜自己重拉一棵新樹——有體力限制的追逐陪練

細步驟解答

採用下列已編譯與 PIE 查證的組合，不新增 C++ 或 Blueprint Task。休息表示停止主動追逐，保留 CharacterMovement 的煞車、重力與被推擠；本題沒有真正的體力屬性。

  1. 停止 PIE，確認 Controller 原本引用哪棵樹。正式基準為 /Game/Fighting/Blueprints/BP_FightingCpuController 的 StateTree 元件，StateTreeRef → StateTree = ST_FightingCpu。不要覆蓋自己的既有練習。

  2. 在 Content Browser 的 /Game/Fighting/AI/ 建立 StateTree，命名 ST_FightingCpuDrill。建立時的 Pick Schema 選 StateTree AI Component；開啟後在 Asset Details 的 Schema 區，把 Context Actor Class 指定為 FightingCpuCharacter。不是一般 Actor，也不是 Player Character。

  3. 在 Parameters 新增 ChaseEnabled（Bool，true）與 ChaseSpeed（Float，400）。這是陪練樹自己的設定，不修改正式樹的七個參數。不要加入「CPU 對手距離與資格」Evaluator：其 Tick 也會更新正式防禦決策，本題不需要。

  4. 建立 Root，再於 Root 下依序新增 Chase、Rest，只有這兩個子狀態；不要加 Enter Condition、攻擊／防禦 Task 或 Global Task。

  5. 選 Chase，在 Tasks 按新增，選「CPU 接近或停止」（FightingCpuMoveTask）。設定如下。Input 欄位用欄位旁的 Binding 選單連接 Parameters，Context 則由 Schema 提供；若 CPU 沒有自動帶入，選 Context 的 Actor。

    移動 Task 欄位 設定／Binding
    Approach（C++ bApproach） true
    Cpu Context → Actor
    Should Approach（bShouldApproach） Parameters → ChaseEnabled
    Approach Speed Parameters → ChaseSpeed
    Parameters Valid（bParametersValid） Parameters → ChaseEnabled
    Can Act（bCanAct） Parameters → ChaseEnabled

    這些 Bool 是給既有 Task 的輸入；真正送移動前，角色的 ApplyAIApproach() 還會檢查控制權、落地與正常行動資格，並未藉此繞過共同規則。

  6. 在移動 Task 的節點設定關閉 Considered for Completion，保持 Task 啟用。再新增 Delay Task：Duration = 1.2、Random Deviation = 0、Run Forever = false，保留它參與完成判定。Chase 的 Tasks Completion 保持 Any。

  7. 在 Chase 的 Transitions 新增 On State Completed → Goto State → Rest。動作 Task 持續送追逐意圖，Delay 單獨決定完成；不要改 All 來等待一直 Running 的移動 Task。離開 Chase 時，移動 Task 的 ExitState() 會呼叫 StopAIApproach()。

  8. 選 Rest，只放 Delay Task：Duration = 2、Random Deviation = 0、Run Forever = false。新增 On State Completed → Goto State → Chase。Rest 不必再放移動 Task，退出 Chase 已撤回主動追逐；CPU 可能有短暫正常煞車，並非硬性凍結座標。

  9. Compile、Save 新樹。開啟 BP_FightingCpuController，在 Components 選繼承的 StateTree 元件，把 StateTreeRef 展開後的 StateTree 改成 ST_FightingCpuDrill，Compile、Save。這裡修改的是 Blueprint 儲存的樹引用，不是 C++ 預設值。

  10. 開啟 stage1，Play。讓 1P 與 CPU 保持可追逐的距離，展示追逐、休息、再追逐。休息中移動 1P，CPU 不應提早恢復主動追逐；不出招也不正式防禦。不要單看 Combat Debug 的 AI: Approach 判斷狀態：Rest 只有 Delay，不會把該文字改成 Rest，欄位可能保留前值。可在 StateTree Editor 的 Debugger 選 PIE 中的執行者對照作用中狀態，再以移動畫面驗收。

  11. 口頭答案核心：移動 Task 負責行為、Delay 負責時限；關閉移動 Task 的完成參與，保留 Delay，讓狀態依計時完成。兩個 Task 同時運作，並非先追逐再開始計時。

  12. 展示後停止 PIE，Controller 引用改回 ST_FightingCpu，Compile、Save，再啟動一次確認正式 CPU 恢復接近與出招；練習樹保留。若 CPU 完全不動，先核對 Controller 引用、Schema／Context、Cpu Binding、ChaseEnabled、ChaseSpeed 與測試移動模式，不先修改 C++。

課堂示範 1｜攻擊位移與地面推擠

設計需求

  • 位移來源：玩家與 CPU 出招時，都依攻擊 Montage 的 Root Motion 水平平移前進、後退或側移；沒有根位移的素材就原地出招。week-08 為了避免滑動，起招時對每個 Montage 播放呼叫 PushDisableRootMotion()，所以 AM_Attack_02 左鉤拳約 90 cm 的前踏不會移動角色。
  • 只取水平：保留出招朝向、重力與地面高度。根骨旋轉與 Z 位移一律丟棄，面向仍由共同面向規則決定。
  • 推擠只看身體：只有雙方 Capsule 實際接觸（容差 2 cm）且都在地面時才推擠。推擠與 Hitbox 命中、Damage Active 區間及扣血完全分開，沒打中也能推，打中也不額外擊退。
  • 三種接觸情境：
    • 相向主動移動：雙方對頂，交給 UE 原生 Pawn Block。
    • 只有一方往前：該方是推動者，被推者讓出多少距離，推動者就跟進多少。
    • 被推者貼牆：被擋住的位移直接捨棄，不累積到下一幀補走。
  • 收尾與交接：舊招開始淡出、被外部停止或接成下一招時，舊招立即停止貢獻位移，並在下一幀清掉殘留速度，避免滑行；新招從自己的播放進度重新計算位移。
  • 受擊時仍可被推：受擊反應中的角色也參與推擠協調。受擊仍鎖住操作，但已成立的被動推擠不會因命中結果中止。
  • 保留不變：出招期間鎖定主動移動與面向、合法選招與預約、命中結算順序。一般行走的雙方互推仍由 1P 既有的 PrePhysics 規則處理，只有攻擊參與時才走本次的新協調。

程式碼增刪異動處

本段要看懂的改動：讓攻擊動畫帶動角色，碰到對手時再協調雙方位置，最後處理收招時的殘留位移。依序閱讀：① 允許攻擊位移，但只留水平平移 → ② 在移動後檢查身體接觸 → ③ 只推動尚未走完的距離 → ④ 收招時停止舊招位移。主要檔案為 FightingCharacter.cpp/.h 與 FightingCameraActor.cpp。

# 攻擊位移與地面推擠
## 玩家體驗
出招時角色依動畫自然前踏、後退或側移，沒有位移的招式原地出招。出招撞到對手時，會把對手往前推，有身體接觸的重量感。

## 規則
- 只取水平位移，不改出招朝向，不離開地面。
- 推擠只看身體接觸，與命中、扣血無關：沒打中也能推，打中也不額外擊退。
- 只有一方往前：推動對方，對方讓多少就跟多少。
- 兩人都往前：互相頂住，誰也推不動誰。
- 對方貼牆：推不動就停，離牆後不補走。
- 接成下一招或收招時，舊招的位移立即停止，不滑行。
- 對方正在出招或受擊，也照樣被推，原動作不中斷。

自由出招、推人、對頂、推到牆邊、X→Y 連招、推擠但沒命中；交換玩家與 CPU 再看一次。

# CPU 自主接近與選招
## 玩家體驗
開場後 CPU 會主動走向玩家，靠近後出招，有時接成兩段連招；打完一組會停一下，讓玩家有反擊或拉開的空檔。

## 規則
- 開場準備完成才開始行動。
- 距離 100 cm 以內算近身，拉開超過 120 cm 才算離開；中間保持原判斷，避免在邊界抖動。

接近後出招、停在 100～120 cm 不抖動、出現合法的 X→Y、收招後才休息、暫停與恢復。

問題：CPU 已經決定要防禦，但需要 0.2 秒才準備好。你的拳頭在 0.1 秒時就打中了它。這一拳擋得住嗎？如果想讓玩家有機會搶先打中，為什麼要保留這段準備時間？

  • 參考答案：擋不住，這一拳仍會扣血，CPU 也會取消這次防禦。決定要擋，不代表已經來得及擋。 準備時間讓玩家有機會在 CPU 防禦生效前打中它；若決定防禦後立刻就能擋，玩家就少了這個機會。
  • 判讀重點：學生能區分「想要防禦」與「已經能擋」，並說明準備時間對玩家有什麼影響。
  • 可以追問：「如果改成準備完成後才打中，而且仍是它正在防的同一組攻擊呢？」答：在正式防禦仍有效時，這一拳會被擋下，不扣血並播放防禦動作。

# CPU 與玩家防禦
## 玩家體驗
玩家按住遠離對手的方向就能擋住攻擊；CPU 偶爾會擋，但需要一點反應時間，玩家出手夠快仍能打中。

## 規則
- 玩家：被打中的那一刻正按住後退（遠離對手）才算防禦。換邊後要按另一邊；跳起、出招中、受擊中不能防。
- CPU：玩家每一組攻擊只決定一次要不要防，120 cm 內有一半機會。決定防禦後要 0.2 秒才擋得住，這段時間被打照樣受傷並放棄這次防禦。
- 同一組 X→Y 不重新決定；防禦維持到這組攻擊結束，之後才休息 0.8 秒。
- 防禦成功不扣血，播放防禦動作；失敗照常受傷。
- 不做上下段、摔技、削血、防禦條。
