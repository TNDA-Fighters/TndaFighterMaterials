課前實作練習

課前實作練習 1｜讓一段看得見的牆可以穿過

細步驟解答

  1. 在 Content Browser 開啟 /Game/Fighting/stage1，Play 模式選 Selected Viewport，出生方式使用既有 Default Player Start。停止 PIE 後，在 World Outliner 搜尋 ArenaBoundary_Wall_00，選取後按 F 聚焦。它位於 Gameplay/ArenaBoundary，是直接放置的 StaticMeshActor。
  2. 在 Details 選取該 Actor 的 StaticMeshComponent，展開 Collision 與 Collision Presets。記錄原值：Preset 為 BlockAll、Collision Enabled 為 Query and Physics（API 名稱 QueryAndPhysics）、Object Type 為 WorldStatic，Pawn 與 Camera 回應皆為 Block。核對 Transform，避免操作時誤移牆面；驗收直接看分享桌面的設定與操作結果。
  3. 分別選取既有 PlayerStart、CpuStart，記下 Location 的 X／Y／Z；保留各自的 Player Start Tag、旋轉與縮放。將兩者移到牆段中央附近的場內。可用的備課候選位置是 PlayerStart 的 X／Y=2500／1800、CpuStart 的 X／Y=2250／1800，Z 各沿用原值。這組水平座標依現行牆面幾何安排，尚未完成這組出生位置的 PIE 排練；開場後先核對實際位置。Wall_00 的內側面在 X=2690，中央 Y=1800，兩個候選位置都在場內且彼此不接觸。
  4. 儲存本題修改的關卡／External Actor，按 Play。先以小幅 W／A／S／D 輸入辨認朝牆方向，再走向 Wall_00 的中央；方向相對遊戲畫面，不能把 D 固定當作世界 X 正向。原本應被牆擋住。若未接近牆就停下，按 Shift+F1 釋放滑鼠，核對兩名角色位置，確認水平間距尚未到 650 cm。本題不調整攝影機上限。
  5. 停止 PIE，回到 Wall_00 的 Collision Presets，選 Custom...，只把 Object Responses > Pawn 改成 Ignore。這一步是將既有組合改成可個別編輯的回應；核對 Object Type、Collision Enabled 與其餘各列回應均和原來相同。不要選 NoCollision，也不要隱藏或刪除牆。
  6. 儲存後再次 Play，以相同路線穿過 Wall_00，現場展示「牆仍可見、1P 能穿過」。通過碰撞厚度後即可停止這輪，避免繼續走出擂台頂面而落下。場外沒有自動回場流程，重測使用新的 PIE。
  7. 另開一輪 PIE，從場內接近相鄰 Wall_01 或 Wall_23 的中央，避開接縫，確認仍被阻擋。讓 CPU 與 1P 一起保持在測試區附近；若原出生位置造成距離限制先介入，可只微調兩個既有出生點的 X／Y，記錄新值，不把任何一人放到場外。現場依序操作指定牆與相鄰牆，請學生指出設定差異並解釋通行結果。
  8. 核對解釋：Source/TndaFighter/Fighting/FightingPlayerCharacter.cpp 的 Move() 收到輸入，DoMove() 呼叫 AddMovementInput()；本題沒有改這些程式。1P 的 Capsule 是 Pawn，牆對 Pawn 改為 Ignore 後不再阻擋這條角色移動路徑；牆的模型與可見設定仍相同，所以外觀保留。相鄰牆沒有修改，仍按原回應阻擋。
  9. 若牆仍擋住 1P，先確認選到 Wall_00 的元件、Pawn 列確為 Ignore，再確認角色沒碰到相鄰牆或 CPU。若角色根本到不了牆，先排除最大間距；不要一口氣關閉所有碰撞。設定、位置與結果的對照，才是本題驗收依據。
  10. 停止 PIE，將 Wall_00 的 Collision Preset 還原成 BlockAll，核對 Pawn／Camera 均為 Block，將兩個出生點還原成步驟 3 記錄的完整位置。只保存本題涉及的關卡與 External Actor，重新 Play 確認指定牆恢復阻擋，再停止 PIE。

課前實作練習 2｜先改 C++、再改 Blueprint，膠囊半徑最後以誰為準？

細步驟解答

準備：確認上一題已還原。開啟 Source/TndaFighter/Fighting/ 下的 FightingPlayerCharacter.cpp、FightingCpuCharacter.cpp，兩個建構子都從 InitCapsuleSize(35.0f, 90.0f) 開始。開啟 /Game/Fighting/Blueprints/ 下的 BP_FightingPlayerCharacter、BP_FightingCpuCharacter，選 Capsule，確認 Shape > Capsule Radius 沿用父類預設 35。全程保持半高 90、縮放 1,1,1，Mesh 與牆設定不變。

每次修改 C++，都先關閉 Editor，保存程式後以 TndaFighterEditor / Win64 / Development 完整建置，成功後重開同一專案。三步連續進行，中途保留 BP 的修改。

  1. 第 1 步：C++ 半徑 35 → 50。 兩個建構子改為 InitCapsuleSize(50.0f, 90.0f)，完整建置並重開。兩個 BP 與新 PIE 角色的半徑都變成 50。原因：此時 BP 還沒有自訂半徑，沿用 C++ 父類提供的預設值，因此父類改成 50，角色也跟著改成 50。
  2. 第 2 步：BP 半徑 50 → 20。 停止 PIE，在兩個 BP 的 Capsule 將 Capsule Radius 改為 20，各按 Compile、Save，再開新 PIE，角色半徑變成 20。這次操作把 20 儲存成 BP 的自訂值，覆寫 C++ 提供的 50。保留這個設定進入下一步。
  3. 第 3 步：保留 BP 的 20，C++ 半徑 50 → 80。 兩個建構子改為 InitCapsuleSize(80.0f, 90.0f)，完整建置並重開。兩個 BP 與新 PIE 角色仍是 20。原因：C++ 的原生預設已改成 80，但 BP 保留了第 2 步儲存的自訂值 20；遊戲生成的是這兩個 BP 角色，所以仍使用 20。C++ 編譯有生效，只是 BP 的自訂值沒有被新的原生預設蓋掉。

課堂驗收： 請學生遠端分享桌面，直接展示 C++ 參數、兩個 BP 的 Capsule 與 PIE 畫面，操作角色碰牆，並口頭說明第 1、3 步為何不同。需要查看遊戲角色的半徑時，按 Shift+F1，在 Outliner 選 PIE 生成的角色，再選 Capsule 查看 Shape。助教的判斷重點是：「第 1 步沿用父類預設；第 3 步已經有 BP 自訂值。」

完成後還原： 關閉 Editor，將兩個 C++ 半徑改回 35.0f，完整建置並重開；在兩個 BP 的 Capsule Radius 旁按 Reset to Default，回到沿用父類預設的 35，各按 Compile、Save。最後開新 PIE 確認兩名角色的半徑 35、半高 90。

課堂示範

課堂示範 1｜同一面牆如何回應角色與攝影機

示範重點

  • 物件、形狀與回應：以 stage1 的 ArenaBoundary_Wall_00 及角色 Capsule 區分看得見的模型與移動碰撞。牆為 WorldStatic + QueryAndPhysics + BlockAll；Object Type、啟用哪些碰撞用途與各 Channel 的 Response 是不同層次。允許 Physics 不等於已勾選 Simulate Physics。
  • 角色與鏡頭使用不同查詢：角色 Capsule 是 Pawn，牆對 Pawn 的回應參與角色移動阻擋；FightingCameraActor.cpp 的建構子將 CameraBoom->bDoCollisionTest 設為 true、ProbeChannel 設為 ECC_Camera。Camera 是這裡的探測 Channel，不是把攝影機 Actor 的 Object Type 改成 Camera。
  • 既有場地配置：共 24 段牆；05～08 是高牆，17～19 是短牆，其餘是基準牆。基準與短牆 Scale X／Y 同為 2.5／0.3，Z 分別為 1.1／0.6。SM_Cube 的 Pivot 在底部角落，保留 Location Z=200、只改 Scale Z，才可維持底部並改變牆頂高度。
  • 已知限制：高牆阻擋 Camera 探測時，SpringArm 會縮短實際鏡頭距離，但 TargetArmLength 仍是期望值。角色可能因鏡頭過近而出框；本週不以雙方始終入鏡為完成條件。
  • 規則分工：場地牆限制角色在場內，MaxFighterDistance 限制 1P 相對 CPU 的水平間距，SpringArm Collision Test 保護鏡頭位置。正常教材 BP 的最大間距為 650 cm，C++ fallback 的 570 cm 不可混寫成 BP 實際值。碰牆不觸發 Ring Out、KO 或回合結束。
  • 概念對照：Blocking Volume 可提供不可見的阻擋區域，本教材使用可見 StaticMeshActor。若用 Unity 協助理解，可把外觀與 Collider 的分工、Layer 碰撞篩選當作近似概念；UE 的 Object Type、Response、Trace Channel 與 CharacterMovement 並非 Unity 類型或生命週期的一對一替換。

課堂示範 2｜碰牆為何會停住，斜向移動為何能沿牆走

示範重點

  • 主動移動入口：玩家的 FightingPlayerCharacter.cpp::DoMove() 與 CPU 的 FightingCpuCharacter.cpp::UpdateTestMovement() 都使用 AddMovementInput()。前者取得玩家兩軸輸入，後者由測試模式提供方向與比例；CharacterMovement 接手處理實際移動。
  • 以牆為方向基準：正對牆是朝牆內推進，切線是沿著牆面，斜向則同時含有兩者。碰撞可能擋住朝牆分量而保留沿牆分量，所以持續有輸入不代表角色一定前進，也不代表完全不能移動。這是平直牆面與一般地面狀態的概念說明，不把接縫、角落或台階行為化約成一條保證公式。
  • CPU 是否真的提供輸入：TestMovementMode=Disabled 時提前返回；取得有效對手方向後，RetreatFromPlayerSlow 使用反向與 0.25 的輸入比例。這個數字是輸入比例，不是保證每秒速度或「半速」。CPU 碰牆不會由此函式自動把模式切回 Disabled。
  • 另一個位移入口：只帶讀 ResolveGroundPushInteraction() 內 MovePairAlongAxis 的局部片段。AddActorWorldOffset(RequestedOffset, true, ...) 以 Sweep 沿途檢查根元件碰撞；AvailableOffset 再用前後位置相減，取得實際完成位移。這是推擠直接要求位移的路徑，不是 CPU 主動移動，也不是 AddMovementInput() 的同義寫法。
  • 判斷依據：一起看輸入來源／模式、碰撞設定與前後位置。動畫仍在走、模式仍為後退，都不能單獨證明角色有位移；CPU 完全不動，也不能直接認定已經碰牆。

課堂實作

課堂實作 1｜把三段短牆加高到基準牆高度

題目

將 /Game/Fighting/stage1 的 ArenaBoundary_Wall_17～19 三段短牆 Scale Z 從 0.6 改為 1.1，使牆頂與鄰接基準牆同高。

保留位置、旋轉、Scale X／Y、Mesh 與碰撞設定。完成後三段牆仍從 Z=200 起算、頂部提高到 Z=310，接縫沒有新增缺口，1P 一般地面移動仍被阻擋；課堂分享桌面，展示外觀、Transform 與碰牆操作，並說明底部不動時牆頂為何升高。

參考答案

  1. 停止 PIE，在 World Outliner 搜尋 ArenaBoundary_Wall_17，選取後按 F 聚焦；再依序記錄 18、19 的 Transform 與 Collision。原 Scale 都是 2.5,0.3,0.6、Location Z 都是 200；X／Y 與旋轉各不相同，保持各自原值。
  2. 按住 Ctrl 在 Outliner 選取這三段，確認剛好三個選取項目。於 Details 的 Transform > Scale 確認比例鎖定圖示已解除；只在 Z 輸入 1.1 並按 Enter，X／Y 保持 2.5／0.3。若多選欄位不好辨認，可逐段修改同一個 Z 欄，不用縮放工具拖曳。
  3. 逐段回讀：Location／Rotation 沒變，Scale 為 2.5,0.3,1.1，Mesh 仍為 /Game/LevelPrototyping/Meshes/SM_Cube，Collision 仍為 WorldStatic + QueryAndPhysics + BlockAll。本題不移牆、不改分類標記或材質。
  4. 比較 16→17→18→19→20 的頂部與接縫。這個 Mesh 本地高度為 100 cm、Pivot 在底角，所以高度從 100×0.6=60 變為 100×1.1=110 cm；底部仍是 200，頂部便由 260 變為 310。場地地板頂面是 Z=210，所以可見牆高是 100 cm，不要把 Location Z 當成牆中心。
  5. 保存本題涉及的關卡／External Actor。Play 後將雙方帶到這三段牆附近，在每段中央朝牆移動，確認 1P 被擋住，能再向內移動；再沿接縫移動，確認沒有新增可穿越缺口。若距離上限先介入，先讓雙方一起接近測試區；若需暫移出生點，只改既有出生點的場內 X／Y，先記錄並在收尾恢復。
  6. 驗收時請學生分享桌面，依序展示三段修改後 Transform、整段外觀及碰牆結果，並口頭說明高度的計算方式。若牆底浮起，先核對 Location Z；若牆變寬，先核對比例鎖是否使 X／Y 也改變。高牆造成鏡頭縮近不等於這題的牆高修改失敗，必要時用編輯器視角核對形狀。
  7. 現場展示完成後停止 PIE，將三段 Scale Z 還原為 0.6；比對原 Transform、碰撞與暫改的出生點，保存並確認三段恢復短牆外觀。

課堂實作 2｜讓 CPU 開場後退，直到被牆擋住

題目

將 /Game/Fighting/Blueprints/BP_FightingCpuCharacter 的 Test Movement Mode 預設值改為 RetreatFromPlayerSlow（往 1P 方向遠離，慢），做出每次 Play 都會主動遠離 1P、碰牆後停在場內的 CPU。

完成成果是保存了該模式的 Blueprint。沿用關卡原有完整碰撞，只修改這項既有設定；CPU 持續保持後退模式時也不能穿牆。課堂分享桌面，停止再 Play 一次，展示開場行為能重現，並說明持續後退模式為何沒有讓 CPU 穿牆。

參考答案

  1. 確認前三項實作的牆面碰撞、半徑、出生點與牆高均已恢復。停止 PIE，開啟 /Game/Fighting/Blueprints/BP_FightingCpuCharacter，按 Class Defaults，在 Details 搜尋 Test Movement Mode；分類是 CPU Test Movement。記錄原值，現行教材為 關閉測試流程（Disabled）。
  2. 下拉選單選 往 1P 方向遠離（慢），對應 EFightingCpuTestMovementMode::RetreatFromPlayerSlow。按 Compile，確認成功後 Save。只改此欄，不新增 AI Controller、Blueprint 節點或碰牆事件。
  3. 開啟 stage1，按 Play 並保持 1P 不輸入。CPU 應從開場持續遠離 1P；到邊界後被牆擋住，繼續留在場內。最大間距規則可能在 CPU 遠離時校正 1P 位置，不能把這個畫面誤認為 CPU 已啟用推擠；本題看 CPU 是否接觸牆、是否持續保持後退模式。
  4. CPU 到牆後按 Pause、Shift+F1，選遊戲中的 CPU，直接查看 Location 與 Test Movement Mode。恢復執行、保持 1P 不輸入，稍後再 Pause 讀取一次；應仍是後退模式，位置留在牆內側且沒有持續穿透。判斷不能只靠行走動畫。
  5. 停止 PIE，再按 Play。確認 CPU 又從開場主動後退，證明修改已保存在 Blueprint 預設值，而不是只改到上一輪執行個體。在分享畫面中指出 Blueprint 設定，並直接重現兩輪開場行為。
  6. 程式依據：Source/TndaFighter/Fighting/FightingCpuCharacter.h 宣告 TestMovementMode；同目錄 FightingCpuCharacter.cpp 的 Tick() 呼叫 UpdateTestMovement()。後退慢速分支以 -DirectionToPlayer、MovementScale=0.25f 呼叫 AddMovementInput()，碰牆後沒有將模式改成 Disabled 的程式。bRunPhysicsWithNoController=true 讓現階段沒有自動 AI Controller 的 CPU 仍可使用這條移動路徑。
  7. 若 CPU 從開場就完全不動，先核對是否改了正確 Blueprint 的 Class Defaults、Compile／Save 是否成功、PIE 是否生成該 CPU，以及對手是否有效。若 CPU 尚未碰牆就停止，核對位置與當次模式；不要新增停止或碰牆程式來湊出預期畫面。
  8. 現場驗收完成後停止 PIE，將 CPU Blueprint 的模式還原為步驟 1 原值，再 Compile、Save；新 Play 確認 CPU 不再主動後退，最後停止 PIE。
