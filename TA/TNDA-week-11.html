參考做法與判讀

參考做法 1：X→X→X→Y，第二攻擊收尾。 以下數值以 week-11 教材專案、60 FPS、CPU AI 關閉、tnda.Debug.CPUDefense on、站距 85 cm 的 PIE 實測確認。

  1. 停止 PIE，改 CommandTable.csv。 用文字編輯器開啟專案根目錄的 _DataTable/CommandTable.csv，把 ID 5 那一列最後兩欄從 ,,FALSE 改成 ,3,FALSE，讓第三段之後可以接第二攻擊（ID 3），以 UTF-8 存檔。
  2. 改 DamageTable.csv。 把 3,第二攻擊,20,32,28 改成 3,第二攻擊,20,32,30，只改第 5 欄 Blockstun，存檔。
  3. Reimport。 在 Content Browser 對 /Game/DataTable/DT_Command 與 /Game/DataTable/DT_Damage 各按右鍵選 Reimport，再雙擊開啟，確認 Row 5 的 Link 是 3、Row 3 的 Blockstun 是 30。
  4. 開 PIE，固定防禦。 開 /Game/Fighting/stage1 按 Play，按右 Ctrl＋F12 打開 Combat Debug；按 ` 開 Console 輸入 tnda.Debug.CPUAI off 與 tnda.Debug.CPUDefense on。
  5. 演示。 走到 CPU 面前，依序按 U、U、U、I：1P 面板的 Attack 依序顯示 ID 1、4、5、3。打完後 Frame Bar 右側 1P 顯示白色 0。實測恢復幀：CPU 與 1P 都在第 90 幀恢復，以第一段的第 0 幀起算。
  6. 還原。 把兩份 CSV 改回 ,,FALSE 與 32,28，再 Reimport 兩張表；Console 輸入 tnda.Debug.CPUDefense auto 與 tnda.Debug.CPUAI on。

  1. 改 CommandTable.csv。 ID 5 那一列最後兩欄改成 ,2,FALSE，讓第三段之後可以接右腳踢頭（ID 2）。

判讀重點

  • 收尾那一段由誰接上：學生要說出 ID 5 原本的 Link 是空白，所以第三段之後接不了任何招；改成 3 或 2 後，第三段出招中按 Y 或 6X，候選只看 ID 5 的 Link。ID 4 的 Link 不能改成 3，因為 ID 4 與 ID 3 都播 AM_Attack_02，匯入時會整表驗證失敗。
  • 硬直的門檻：學生要用「命中幀＋Blockstun－長度」說明。第二攻擊是 10＋Blockstun－40，要 ≥ 0，Blockstun 至少 30；右腳踢頭是 14＋Blockstun－70，Blockstun 至少 56。實測門檻兩側都成立：第二攻擊 29／30／31 對應 －1／0／＋1，右腳踢頭 55／56／57 對應 －1／0／＋1。
  • 前面幾段不影響結果：學生能說出收尾前接了幾段，只會把整條時間軸往後推，結果仍由最後一段決定。X→Y 改 Blockstun 30 也是 0，和 X→X→X→Y 相同。
  • 改共用的 Damage 列會牽動別的招：第二攻擊的 Damage 3 也是 ID 4 在用，Blockstun 改成 30 後，X→X 被防也從 －2 變成 0。右腳踢頭只改 Blockstun 時，踢頭收尾被打中仍是 －7。
  • 不動 DamageTable 的另解：在 CommandTable 新增一列收尾招，Montage 用 AM_Attack_02、Damage 改用既有的 2（踢頭的硬直），再由 ID 5 的 Link 接到這一列。依算式 10＋46－40＝＋16，不必改任何硬直；這個改法符合題目限制，但本次沒有實測。上面「Blockstun 至少 30／56」的門檻，只適用沿用原本 Damage 列的改法。

可以追問

  • 「X→X→X→6X 被防是 0，被打中反而是 －7，為什麼？」答：打中查的是 Hitstun 49，只改了 Blockstun；要讓打中也不吃虧，Hitstun 也要至少 56。
  • 「同一套連段，CPU 改成 AI 自己抽防禦時，你還能保證不吃虧嗎？」答：只要收尾那一段被防住，結果就是同一個數字；CPU 若沒防，結果改看 Hitstun。

教師備註：數值效果以腳本在記憶體改寫資料表後的 PIE 實測確認，人手按鍵的接招時機與學生端 CSV 存檔、Reimport 的操作流程沒有實際操作驗證。腳本在每一段開始後第 4 幀送下一個輸入，交給預約在 Enable 接出。

程式追蹤

課前預習的兩條閱讀路徑，在這裡連同呼叫順序展開。原始碼取自 Projects/TndaFighter-worktrees/dev-week-11，採用 HEAD c718ae99，在 week-11（61e68432）之後只改了 Editor 工具與文件，不影響本區的程式。

追蹤路徑一｜同樣按 X，程式怎麼決定出哪一個 ID？

空檔按 X 一定是 ID 1，ID 1 出招中按 X 卻是 ID 4，差在哪裡？ 共用入口先看角色是不是正在出招，再把「有沒有 Link 集合」交給同一個選招函式。

  1. 玩家按鍵進入共用入口。 Source/TndaFighter/Fighting/FightingPlayerCharacter.cpp 的 AFightingPlayerCharacter::Attack() 取樣方向後呼叫 SubmitCommand()；玩家版確認有 Controller，再交給 FightingCharacter.cpp 的 AFightingCharacter::SubmitCommand()。CPU 出招也走同一個入口。
  2. 不在出招中：起手。 SubmitCommand() 確認角色在 Neutral 或 Defending 後，呼叫 Source/TndaFighter/DataTable/TndaCommandReader.cpp 的 UTndaCommandReader::TrySelectCommand()，它以 Link＝nullptr 呼叫 SelectCommand()。
  3. 起手只留有起手資格的列。 SelectCommand() 走訪已排序的 Reader->Commands，!Link && !Candidate.bOpener 的列直接跳過，再找第一個 Attack 相同、方向符合的列。ID 4、5 的 bOpener 是 false，所以空檔按 X 選到 ID 1。
  4. 出招中：先看能不能預約。 回到 SubmitCommand() 的 IsAttacking() 分支。IsCommandPreorderOpen() 要求目前招式的 Link 不是空的、動畫位置在 Preorder～Disable 之間；接著呼叫 TrySelectLinkedCommand()，把目前招式的 CurrentAttack.Link 傳進 SelectCommand()。
  5. 接招只留 Link 列出的 ID。 這次 SelectCommand() 先用 Link->Contains(Candidate.Id) 排除集合外的列，不再看 bOpener。選到的列和目前招式同一份 Montage 時，SubmitCommand() 回傳拒絕。
  6. 到 Enable 才真的接出。 通過的輸入存進 CommandBuffer，有效 0.5 秒；動畫到 Enable 時 ConsumeCommandBuffer() 再選一次並呼叫 StartAttack() 交接新招。

這張圖只回答「同一個按鍵為什麼選到不同 ID」。兩條路最後都進 SelectCommand()，差別只在有沒有傳入 Link。

追蹤路徑二｜幀優勢在什麼時候、用哪兩個數字定案？

X 被防住的 ＋3 是誰算出來的？ 命中時先記下這次攻防，之後每一幀檢查誰先恢復，先恢復的一方一出現就用對方剩下的時間定案。

  1. 命中時記下這次攻防。 FightingCharacter.cpp 的 TryApplyHit() 確認合法命中、問完防禦意圖後，呼叫 RecordExchangeHit(Target, bDefenseHit)：把受擊方記成 ExchangeDefender，記下是不是被防，也順便依受擊方當下的攻擊階段算出破招、截擊或確反。
  2. 每一幀命中結算後檢查。 HandleWorldPostActorTick() 在命中、硬直與收招都套用後，對雙方各呼叫一次 UpdateFrameAdvantage()。
  3. 雙方都還沒恢復就不定案。 UpdateFrameAdvantage() 把雙方是否可行動、攻擊方剩下的動畫時間（GetAttackRemainingSeconds()）與防守方剩下的硬直（GetStunRemainingSeconds()）交給 ResolveFrameAdvantage()。兩人都不能動時回傳 false，連段打到一半就停在這裡。
  4. 先恢復的一方決定正負號。 攻擊方先恢復時，數字是防守方剩下的硬直，換成設計幀後是正數；防守方先恢復時，數字是攻擊方剩下的動畫時間，取負號。以 X 被防為例：第 30 幀攻擊方恢復，CPU 的 Blockstun 還剩 3 幀，結果是 ＋3。
  5. 雙方各存一份，寫進 Log。 攻擊方存 Frames、防守方存 -Frames，Frame Bar 右側讀的就是 1P 那一份；Log 寫一行 FrameAdvantage: ... attacker_frames=+3 ...。
  6. Frame Bar 另外記格子。 FightingPlayerCharacter.cpp 在每一幀 World Tick 結束時（HandleWorldTickEndForFrameBar() → SampleFrameBar()）把雙方的狀態交給 FightingFrameBar.cpp 的 FFightingFrameBarRecorder::Sample()，一格一個設計幀；雙方都恢復後停止記錄，結果保留到下一次攻防。

這張圖只回答「幀優勢何時定案、取哪個剩餘時間」。定案發生在先恢復的那一幀，不等後恢復的一方。

  • 兩個時機看不同欄位：學生要說出空檔選招只看 Opener，連段中只看目前招式的 Link。ID 2 是 FALSE，空檔被跳過，6X 落到 Keys 沒寫方向的 ID 1；第三段 ID 5 出招中，候選只剩 Link 裡的 ID 2，6X 符合，所以出踢頭。
  • 只加 Link、不設 Opener：ID 2 在空檔仍可起手，空檔與連段中按 6X 都出 ID 2。它只是「也能接在連段裡」，不是專屬招。設與不設的差別是出拳（ID 1）對踢頭（ID 2），不看 Combat Debug 也分得出來。
  • 和課前實作的關係：課前選右腳踢頭收尾的學生已經改過 ID 5 的 Link，這題只多改 ID 2 的 Opener；課前改過的 DamageTable 已經還原，這題不需要。課前選第二攻擊收尾的學生，可以照同樣想法把 ID 3 設 FALSE、ID 5 的 Link 設 3：空檔按 Y 不會出任何招，因為能起手的 ID 1、ID 2 都要按 X；X→Y 仍可出 ID 3，因為 ID 1 的 Link 本來就有 3。這個另解依選招規則推得，尚未實測。
  • 新增列的另解：學生也可以新增一列專屬招，但 Montage 只能用既有的三份，動作一定和某一招相同，只能靠 Attack 的 ID 區分。這時 FALSE 與空白的差別取決於輸入：用 4,X 時，空檔分別出 ID 1 與新列，看得出差別；用 Y 或 6,X 時，空檔一律由 ID 更小的既有列（ID 3、ID 2）搶先，兩者畫面相同。這組結果已實測；學生能用排序規則說明，也算理解。
  • 常見錯誤：Link 指到和目前招式同一份 Montage 的列，例如把 ID 5 的 Link 設成 1（兩者都播 AM_Attack_01，也讓 1→4→5→1 繞成一圈），匯入時會整表驗證失敗，開 PIE 時跳出驗證失敗對話框並停止。Opener 寫成 false 小寫也會整表失敗。把 ID 1 的 Opener 改成 FALSE，空檔按 X 不會出任何招，Y 仍出 ID 3。

可以追問

  • 「把 ID 4 的 Opener 改成空白，空檔按 X 會出 ID 4 嗎？」答：不會，仍是 ID 1。兩列都沒寫方向，ID 小的 ID 1 排在前面；本次實測連按三下仍是 1→4→5。
  • 「只把 ID 2 設成 FALSE，忘了改 ID 5 的 Link，會發生什麼？」答：匯入不會失敗，但沒有任何 Link 指到 ID 2，Output Log 會警告這一列永遠無法使用，整場都使不出右腳踢頭。

教師備註：連段 ID 1→4→5→2 與空檔 4X 落到 ID 1，以腳本在記憶體改寫 DT_Command 後的 PIE 實測確認，腳本直接送出攻擊語意。空檔 6X 在 ID 2 設 FALSE 時落到 ID 1、刪掉 FALSE 後回到 ID 2，以及第二攻擊的另解，都依選招規則推得，尚未實測；人手按住前進時角色會往前走，選招結果應相同，但沒有實際操作驗證。整表驗證失敗的三種情況（同 Montage、循環、小寫 false）依原始碼推得，本次沒有在 PIE 實測對話框。
