判讀重點

  • 輸入為什麼選到 ID 6：學生要用排序說明。ID 6 與 ID 3 的 Priority 都是 0，ID 6 的 Keys 有方向，排在 ID 3 前面；輸入帶著那個方向時先符合 ID 6。沒帶那個方向時 ID 6 不符合，往下找到 Keys 沒寫方向的 ID 3。
  • 把 Priority 改大的做法：學生若把 ID 6 改成 Keys=Y、Priority=1，ID 6 排到最前面，不帶方向或帶 6 都出越頂，ID 3 從此按不出來。實測兩種輸入都選到 ID 6。這個改法合法，但學生要說得出「第二攻擊被搶走」，演示第二件事時要換別的鍵，例如 6X 出右腳踢頭。
  • 距離為什麼越得過：學生要說出軌跡沿起跳面向走完水平距離，起跳時站距小於水平距離才會從對手上方通過。實測距離 150 cm 時，站距 100 cm 越過、180 cm 沒越過。
  • 方向與面向是兩件事：做法 2 按的是後退鍵，越頂仍朝 CPU 跳。輸入的 4 只用來選招，軌跡方向取起跳那一幀的角色面向。
  • 高度與曲線：改 Apex Height Cm 或曲線只改變畫面上的節奏與高度，在場中央不影響越不越得過；曲線不合法時（高度曲線兩端不是 0、水平進度曲線兩端不是 0 與 1 或中途倒退），整張招式表驗證失敗。高度與曲線的各種改法沒有逐一實測。

可以追問

  • 「越頂跳到一半，你在 Details 把距離改成 400，這一次落點會變嗎？」答：不會。起招時已經抄下距離，這一次照 300 跳完，下一次越頂才用 400。
  • 「做法 2 之後，按住後退防禦時再按 I 會怎樣？」答：防禦中仍可以起手，選招結果是 ID 6。這一點依 SubmitCommand 推得，實際按住後退鍵的操作沒有實測。

程式追蹤

追蹤路徑一｜按下 U 的那一刻，程式怎麼選到 ID 2 而不是 ID 5？

ID 4 出招中按著朝對手的鍵再按 U，為什麼出右腳踢頭？ 方向在按鍵當下換成 6，排序在匯入時就讓 ID 2 排在 ID 5 前面。

  1. 按鍵當下取樣方向。 Source/TndaFighter/Fighting/FightingPlayerCharacter.cpp 的 AFightingPlayerCharacter::Attack() 呼叫 SampleAttackDirections()；它經 TrySampleMoveAction() 讀移動輸入的當下值，用攝影機右方換成世界方向，再交給 ClassifyRelativeDirection() 和對手方向比較，得到 Forward6 就放入 6、Backward4 就放入 4。
  2. 進入共用入口。 玩家版 SubmitCommand() 確認有 Controller，交給 FightingCharacter.cpp 的 AFightingCharacter::SubmitCommand()。
  3. 出招中先看能不能預約。 IsAttacking() 分支呼叫 IsCommandPreorderOpen()，通過後用 TrySelectLinkedCommand() 帶入目前招式的 CurrentAttack.Link，檢查有沒有合法候選；選到同一份 Montage 就拒絕。
  4. 存下攻擊語意與方向。 CommandBuffer.Submit(Command, Directions, ...) 把這次的 X 與 [6] 一起存起來，有效 0.5 秒。接招窗口已開就立刻 ConsumeCommandBuffer()，否則回傳 Buffered。
  5. 到 Enable 用存下的方向重選。 HandleCommandLinkNotify() 在 Enable 標記呼叫 ConsumeCommandBuffer()，它讀出預約裡的 Directions，再呼叫一次 TrySelectLinkedCommand()，最後 StartAttack() 交接。
  6. 排序在匯入時完成。 Source/TndaFighter/DataTable/TndaCommandReader.cpp 的 Prepare() 用 Commands.Sort 排成 Priority 降冪、有方向優先、ID 升冪。SelectCommand() 依序跳過不在 Link 內的列，回傳第一個攻擊語意相同、方向符合的列：ID 2（6,X）排在 ID 5（X）前面，帶 6 時先符合 ID 2。

這張圖只回答「6 在什麼時候決定、ID 2 為什麼勝出」。接招那一刻用的是按鍵當下存下的方向，不重新讀方向鍵。

追蹤路徑二｜越頂的軌跡參數從哪裡來，每一幀怎麼變成角色位置？

AM_CrossOver 上的 200 cm 與 110 cm，怎麼變成角色在空中的位置？ 起招時抄一份參數，之後每一幀依動畫位置算出進度，再放置角色。

  1. 資料列認成無傷害招式。 TndaCommandReader.cpp 的 Prepare() 在 Hitbox 與 Hurtboxes 都空白時設 bNoDamage；TndaCommandValidation::ValidateTiming() 再確認 Montage 也沒有 Damage 標記，兩邊不一致就整表拒絕。
  2. 起招時讀標記並快照。 FightingCharacter.cpp 的 StartAttack() 呼叫 FFightingAttackTiming::ReadMontage()。遇到 UFightingAirborneArcNotifyState 時，記下起跳與落地秒數，並把 HorizontalDistanceCm、ApexHeightCm 與兩條曲線複製進 SelectedTiming；交接成功後寫入 AttackTiming。
  3. 每一幀先推進離地段。 AFightingCharacter::Tick() 先呼叫 UpdateAirborneArc()，再呼叫 UpdateAttack()。
  4. 到起跳秒數就起跳。 UpdateAirborneArc() 以 GetAttackPosition() 取動畫位置；位置進入離地段時呼叫 BeginAirborneArc()：記下起跳點與角色前方、記下對手是否在前方、把對 Pawn 的碰撞改成 Ignore、切成 MOVE_Flying。
  5. 依進度放置位置。 進度 Alpha 由動畫位置換算，AirborneArcAt(Alpha) 用水平進度曲線乘上距離、高度曲線乘上頂點高度。先水平掃掠，撞到牆就停在牆前；再垂直掃掠到目標高度，最後 SetActorLocation()。
  6. 到落地秒數就落地。 腳下有可站立地面時呼叫 LandAirborneArc()：切回 MOVE_Walking，和對手重疊就推開，恢復 Pawn 碰撞。腳下沒有地面時改成 MOVE_Falling，自然落下站穩後才落地。

這張圖只回答「軌跡參數從哪來、何時套用」。參數在起招時抄下，位置每一幀由動畫進度決定，不靠動畫的根位移。

課堂示範 1｜回身劈山這招怎麼做出來

設計需求

  • 回身劈山：越頂（ID 6，6Y）越過對手後，在空中按 6X，落地立刻接出右腳踢頭（ID 2），而且轉身朝對手踢。
  • 相對方向分支：設定一直是 6。1P 站在 CPU 左邊時，按住 D 再按 I 起跳；越過之後 CPU 在左邊，朝 CPU 的鍵變成 A，所以要改按住 A 再按 U。還按著 D 時，那是 4X，接不出來。
  • 兩道閘門：越過對手之後才受理空中預約；落地站穩、腳下是擂台，才消耗預約接招。撞牆被擋、落點被推回起跳側、落在牆頂或場外，都不接。
  • 離地軌跡是資料：距離、頂點高度與兩條曲線放在 AM_CrossOver 的 Airborne Arc 標記上，在 Montage Editor 調整，不改 C++。
  • 空中不互撞：離地期間本角色不擋 Pawn，所以能從對手上方通過；落地重疊時推開。
  • UE 提供與遊戲自訂的分界：UE 提供 Anim Notify State、CharacterMovement 的移動模式與碰撞掃掠；起跳、軌跡、越過判定與接招閘門都是教材專案自己定義的規則。
