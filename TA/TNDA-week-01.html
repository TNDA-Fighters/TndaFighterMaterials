課前預習

使用方式

本文件用來檢查學生能否正常使用開發環境，以及是否已從操作結果辨認 Third Person 四種玩法。環境安裝屬於課前條件，不占用兩組各 30 分鐘的實作時間。

教材與環境前置條件

  • Unreal Engine 5.8。
  • Visual Studio 2026，已安裝 Unreal C++ 開發所需工作負載與元件。
  • GitHub Desktop。
  • 從 ThirdPersonTemplate.uproject 產生 ThirdPersonTemplate.sln。
  • 使用 Visual Studio 2026 開啟 ThirdPersonTemplate.sln，按下 F7（Build Solution）完成方案編譯，並確認沒有編譯錯誤。
  • 編譯完成後按下 F5（Start Debugging）啟動 Unreal Editor，確認專案可以開啟並正常進入 PIE。
  • ThirdPersonTemplate 教材專案包含以下關卡：
  • /Game/ThirdPerson/Lvl_ThirdPerson
  • /Game/Variant_Combat/Lvl_Combat
  • /Game/Variant_Platforming/Lvl_Platforming
  • /Game/Variant_SideScrolling/Lvl_SideScrolling

課前實作 1｜比較四種 Third Person 玩法（30 分鐘內）

給學生看的題目

使用 PIE 依序體驗 Lvl_ThirdPerson、Lvl_Combat、Lvl_Platforming 與 Lvl_SideScrolling。整理四種玩法在角色操作、鏡頭、關卡互動與遊戲目標上的差異，並為每個關卡留下一張能看出特色的執行畫面。

教學目的

讓學生先從玩家體驗辨認範本差異，知道 Variant 是可拆解與改造的專案起點，不是四套彼此無關的引擎功能。

完整操作

  1. 開啟 ThirdPersonTemplate，確認目前沒有編譯錯誤。
  2. 在 Content Browser 依序開啟四個關卡。
  3. 每次切換關卡後啟動 PIE，實際操作角色並觀察鏡頭、移動能力、場景互動與可見 UI。
  4. 每個關卡擷取一張能辨認特色的畫面。
  5. 整理比較表，最後選出較適合近戰遊戲原型的起點。

參考答案與教學基準

關卡 應辨認的核心差異
Lvl_ThirdPerson 標準第三人稱移動、跳躍、自由視角與基礎關卡。
Lvl_Combat 徒手攻擊、連段、AI 對手與場景內血條。
Lvl_Platforming 衝刺、牆跳與更強調精準移動的平台玩法。
Lvl_SideScrolling 固定鏡頭、平面移動限制、拾取物與橫向平台互動。

學生的文字不必和表格一致，但必須以實際操作觀察為依據。選擇近戰遊戲起點時，以 Combat 最直接；若學生選擇其他 Variant，只要能說明取捨，不直接判錯。

完成判斷與證據

  • 四個關卡都各有一張 PIE 畫面。
  • 比較表至少涵蓋操作、鏡頭、互動與目標中的三項。
  • 選型理由能對應到所選 Variant 的實際特色。

還原方式

本題只切換並執行關卡，不應修改資產。若誤存關卡變更，使用 GitHub Desktop 檢查差異，只還原本題造成的檔案變更。

常見問題

  • 找不到關卡：確認 Content Browser 沒有啟用只顯示特定資料夾或資產類型的篩選。
  • PIE 出現錯誤地圖：先確認目前開啟的關卡名稱，再按 Play。
  • 操作方式不同：以各關卡內建提示與實際反應為準，不要求四個 Variant 使用完全相同的輸入。

課前實作 2｜讓專案從 Combat 關卡開始（30 分鐘內）

給學生看的題目

把編輯器啟動時開啟的關卡，以及遊戲使用的預設關卡，都改成 Lvl_Combat。關閉並重新開啟專案，確認編輯器會直接進入 Combat 關卡，而且 PIE 可以正常操作角色。

教學目的

讓學生分清楚「目前開啟的關卡」與「專案預設關卡」，並熟悉會寫入專案設定的基本操作。

完整操作

  1. 開啟 Edit > Project Settings。
  2. 進入 Project > Maps & Modes。
  3. 將 Editor Startup Map 設為 /Game/Variant_Combat/Lvl_Combat。
  4. 將 Game Default Map 設為 /Game/Variant_Combat/Lvl_Combat。
  5. 關閉 Project Settings，確認設定已寫入 Config/DefaultEngine.ini。
  6. 關閉並重新開啟專案，確認目前關卡是 Lvl_Combat。
  7. 啟動 PIE，確認角色能移動並使用 Combat 玩法。

參考答案與教學基準

兩個欄位都應顯示 Lvl_Combat。重新開啟專案會驗證 Editor Startup Map；Game Default Map 則以設定頁或 DefaultEngine.ini 的值確認。單純在目前關卡按 Play，不足以單獨證明兩個欄位都已設定。

完成判斷與證據

  • 設定畫面同時顯示兩個 Lvl_Combat。
  • 重新啟動後目前關卡為 Lvl_Combat。
  • PIE 可正常控制 Combat 角色。

還原方式

課堂將沿用 Combat 關卡，因此學生可保留設定。若要回到教材原始狀態，將 Editor Startup Map 與 Game Default Map 都改回 /Game/ThirdPerson/Lvl_ThirdPerson。

常見問題

  • 只改了一個欄位：重新檢查 Maps & Modes 內的兩個 Map 欄位。
  • 重新開啟後仍是舊關卡：確認選到的是 Lvl_Combat 資產，而不是只在 Content Browser 選取它。
  • GitHub Desktop 出現 DefaultEngine.ini 變更：這是本題預期結果；應確認差異只包含兩個 Map 設定。

課堂示範

示範 1｜用 Variant_Combat 看懂 Gameplay Framework

主題

以 Lvl_Combat.umap 為入口，說明關卡、GameMode、PlayerController、CombatCharacter、CombatEnemySpawner 與 CombatEnemy 之間的關係。先比較 Unity 常見的 Scene 配置，再帶學生看懂玩家如何依 GameMode 設定建立，以及關卡中的 Spawner 如何生成 Enemy。

目的

  • 讓學生分清楚哪些物件預先放在 Lvl_Combat 裡，哪些物件要等 PIE 開始後才建立。
  • 說明 GameMode 提供玩家使用的 PlayerController 與 Character 類別，PlayerController 再控制建立好的 CombatCharacter。
  • 說明 BP_CombatActivationVolume 如何啟動第一個 CombatEnemySpawner，以及第一個 Spawner 耗盡後如何接著啟動另外兩個 Spawner。
  • 用 Unity 對照說明兩套引擎都會用 Component 組合功能；Unreal 另外提供已組好常用 Component、用途明確的 Actor 子類別。
  • 讓學生用最簡單的方式分清楚 AActor、APawn 與 ACharacter，並理解 AController 的 Possess 對象必須是 Pawn 或其子類別。
  • 提醒 Unity 與 Unreal 的概念對照只用來協助理解，兩套引擎的類型與生命週期並非一對一。

過程概述

  1. 先用 Unity 常見的 Scene 配置對照 Variant_Combat，指出 Unity 可能直接放玩家 GameObject 與生怪 GameObject；這份 UE 教材則把玩家建立交給 GameMode，關卡內只預先放置 Spawner。
  2. 開啟 Lvl_Combat，在 World Settings 指出 BP_CombatGameMode，再從 World Outliner 確認 4 個 PlayerStart 與 3 個 BP_CombatEnemySpawner。同時確認 CombatCharacter 與 CombatEnemy 都不是預先放好的固定角色。
  3. 查看 BP_CombatGameMode 的 PlayerController 與 Character 類別設定。進入 PIE 後，確認 Unreal 依設定建立兩個不同物件，再由 PlayerController 控制 CombatCharacter；PlayerStart 只提供出生位置。
  4. 沿著 BP_CombatActivationVolume → BP_CombatEnemySpawner → CombatEnemy 說明敵人生成。玩家進入指定區域後才啟動第一個 Spawner，第一個 Spawner 耗盡後再啟動另外兩個 Spawner。
  5. 用 Camera 對照兩套引擎的 Component 組合：Unity 的 Camera 是 GameObject 掛上 Camera Component；UE 的 ACameraActor 內仍有 UCameraComponent，Actor 並沒有取代 Component。
  6. 補充 APointLight、AStaticMeshActor 與 AAmbientSound 等例子，說明 UE 常提供已組好 Component、可以直接放進關卡的 Actor。需要把功能加入既有 Actor 時，仍可直接增加對應 Component。
  7. 最後用 AActor → APawn → ACharacter 收束類別關係。說明一般 Actor 能被程式操作，但只有 Pawn 或其子類別能被 Controller Possess，再請學生用 CombatEnemySpawner、CombatCharacter 與 CombatEnemy 說明各自屬於哪一類。

示範 2｜從按鍵走到 Input Action

主題

以 Variant_Combat 的連段攻擊為例，沿著 PlayerController 啟用 IMC → IMC 配對按鍵與 IA → Character 綁定 IA 並執行行為，說明 Enhanced Input 的責任分工與分層原因。

目的

  • 讓學生看懂 按鍵 → IMC → IA → Character 的最小輸入路徑。
  • 用一句話分清楚四個責任：PlayerController 啟用 IMC、IMC 配按鍵、IA 代表動作、Character 執行動作。
  • 說清楚 BP_CombatPlayerController 只啟用整張 IMC_Combat，按鍵與 IA 的配對則設定在 IMC 資產內。
  • 說明多個實體按鍵可以共用同一個 Input Action，不需要複製攻擊程式。
  • 用換按鍵、換輸入情境與改攻擊內容三種變動，解釋 Enhanced Input 為何拆成不同責任。
  • 為課堂實作新增 U → IA_ComboAttack 的 Mapping 做準備。

過程概述

  1. 在 Lvl_Combat 執行 PIE，以滑鼠左鍵觸發連段攻擊，先讓學生看到輸入結果。
  2. 查看 BP_CombatPlayerController 與 IMC_Combat，說明 PlayerController 只啟用整張輸入表；真正的 LeftMouseButton／Gamepad_RightShoulder → IA_ComboAttack 配對寫在 IMC 裡。
  3. 開啟 IA_ComboAttack，說明 IA 代表「連段攻擊」這個玩家意圖，不綁死某一顆按鍵；Boolean、Pressed、Released 與 Modifier 本週只辨認位置。
  4. 查看 BP_CombatCharacter 與 CombatCharacter.cpp，說明 Character 綁定 IA_ComboAttack 的 Started，再沿著 ComboAttackPressed → DoComboAttackStart → ComboAttack → Montage_Play 追到 AM_ComboAttack。
  5. 用「換按鍵只改 IMC、換輸入情境由 PlayerController 管理、改攻擊內容才動 Character」解釋分層原因，並提醒這是本專案的責任切法。
  6. 最後用四點收束：PlayerController 啟用 IMC、IMC 配按鍵、IA 代表動作、Character 執行動作，再銜接只需新增 U 鍵 Mapping 的課堂實作。

課堂實作

課堂實作 1｜讓 U 鍵也能攻擊

給學生看的題目

在不移除滑鼠左鍵的前提下，讓鍵盤 U 鍵也能觸發相同的連段攻擊。完成後分別使用滑鼠左鍵與 U 鍵測試，確認兩種輸入都會執行同一個功能。

教學目的

確認學生能修改既有 IMC 映射，並理解「增加輸入來源」不等於「複製一套攻擊邏輯」。

教材專案前置條件

  • 使用 ThirdPersonTemplate 的 Lvl_Combat。
  • /Game/Variant_Combat/Input/IMC_Combat 已有 Left Mouse Button → IA_ComboAttack。

參考操作

  1. 開啟 IMC_Combat。
  2. 找到 IA_ComboAttack 的既有滑鼠左鍵映射。
  3. 在同一個 Input Action 下新增一筆 Mapping。
  4. 將新 Mapping 的 Key 設為鍵盤 U，保留滑鼠左鍵那一筆。
  5. 儲存 IMC_Combat，進入 PIE。
  6. 分別按滑鼠左鍵與 U 鍵，確認兩者都觸發連段攻擊。

參考答案與基準

IMC_Combat 內應同時存在 Left Mouse Button → IA_ComboAttack 與 U → IA_ComboAttack。不需要在 Character 內新增第二套攻擊事件。

完成判斷與證據

  • IMC 畫面可同時看見兩筆映射。
  • PIE 中兩個按鍵都能觸發攻擊。
  • 學生能指出兩個按鍵最後共用的是 IA_ComboAttack。

還原方式

若要回到教材原始狀態，刪除 U 鍵那一筆 Mapping，保留滑鼠左鍵映射後儲存。

常見問題

  • 新增了另一個 IA：刪除多餘 IA，改在既有 IA_ComboAttack 下增加 Mapping。
  • U 鍵無反應：確認新 Mapping 的 Key 是鍵盤 U，且 PIE Viewport 已取得焦點。
  • 滑鼠左鍵失效：檢查是否誤把原本 Mapping 改成 U，而不是新增一筆。

課堂實作 2｜把移動速度調成兩倍

給學生看的題目

把 Combat 操控角色的移動速度調成目前的兩倍。完成後進入 PIE，比較修改前後從同一位置走到同一目標所需的時間。

教學目的

讓學生從 Character 的元件設定找到移動參數，並以可重複的遊戲內比較判斷修改是否生效。

教材專案前置條件

  • /Game/Variant_Combat/Blueprints/BP_CombatCharacter 的 Character Movement 可正常使用。
  • 原始 Max Walk Speed 為 400 cm/s。

參考操作

  1. 開啟 BP_CombatCharacter。
  2. 在 Components 選取 Character Movement。
  3. 在 Details 搜尋 Max Walk Speed。
  4. 將數值由 400 改為 800。
  5. Compile、Save，進入 Lvl_Combat 的 PIE。
  6. 從同一個起點朝同一個目標移動，比較修改前後的時間或錄影。

參考答案與基準

目標值為 800 cm/s。這代表角色的最大步行速度設定為原本兩倍，不代表短距離實測時間一定精準減半；加速度、路線與計時誤差都會影響結果。

完成判斷與證據

  • BP_CombatCharacter 的 Max Walk Speed 顯示為 800。
  • Blueprint 編譯沒有錯誤。
  • PIE 中角色明顯比原始設定移動得快，且比較使用同一起點與目標。

還原方式

將 Max Walk Speed 改回 400，Compile 並 Save。

常見問題

  • 改到錯誤角色：確認資產是 BP_CombatCharacter，不是其他 Variant 的 Character。
  • 找不到欄位：先選取 Character Movement 元件，再搜尋完整欄位名稱。
  • 改完沒有差異：確認已 Compile，且 PIE 使用的是 Lvl_Combat 與正確 Character。
