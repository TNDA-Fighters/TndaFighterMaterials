課前預習

課前預習 1｜Frame Data 的四段時間從哪裡來？

時間詞彙。 Startup 是開始後尚未生效，Active 是可產生命中候選的區間，Link 是 Active 結束後到接招截止的階段，Recovery 是窗口關閉後到原招結束。Preorder 另表示「開始接受下一招預約」；Enable 表示「可立即交接」。Preorder 可以早於 Active，並不是四階段中的第五階段。

素材路徑。 開 /Game/Fighting/Anims/AM_Attack_01，找 Damage State 和 CommandLink Preorder／Enable／Disable。從 Source/TndaFighter/Fighting/FightingCommandLink.cpp::FFightingAttackTiming::ReadMontage() 追到 IsValid()、PhaseAt()：每種 Notify 必須恰有一個，且 0 ≤ Preorder < DamageBegin < DamageEnd < Enable < Disable < Length。PhaseAt() 以 DamageBegin、DamageEnd、Disable 分界；Link 階段開始不代表 Enable 已開。

可預約與可交接：現在能先記住輸入，還是能接出下一招？ CanPreorder() 判斷目前素材位置是否允許接受預約；CanLink() 判斷目前素材位置是否允許交接到下一招。兩者都只回傳時間條件是否成立，函式本身不會保存輸入或播放動畫；實際受理與交接由角色的 SubmitCommand()／ConsumeCommandBuffer() 處理。

目前的素材位置 CanPreorder() CanLink() 合法輸入通過角色狀態檢查後的處理
Preorder 之前 false false 拒絕預約，不會替玩家保存到窗口開啟
Preorder 起，到 Enable 之前 true false 先存入 Buffer，回傳 Buffered；目前這招繼續播放
Enable 起，到 Disable 之前 true true 可立即嘗試消耗 Buffer，下一招播放成功才回傳 Started
Disable 起 false false 預約與接招窗口都已關閉；清除舊預約，也不接受新預約

這張表以有效的攻擊時間資料為前提。CanPreorder() 的區間是 [Preorder, Disable)，CanLink() 是 [Enable, Disable)；方括號表示包含起點，右括號表示不含終點。可接招區間包含在可預約區間內，所以到了 Enable，CanPreorder() 仍然是 true。 角色的 FightingCharacter.cpp::RefreshAttackTiming() 以實際 Montage 位置更新狀態，不累加 Tick 幀數。

具體例子：同樣按下一招，按下的位置決定先等還是立即接。 假設 Preorder 在素材 0.1 秒、Enable 在 0.5 秒、Disable 在 0.8 秒；這些是說明用數字，不是專案資產的實際設定。以下各案例獨立從第一招開始，先採 PlayRate＝1，假設輸入符合合法後續、角色狀態正常、沒有中斷，且下一招可成功播放。

  • 素材 0.05 秒按下：太早。 尚未到 Preorder，輸入被拒絕。即使稍後到了 Enable，也不會記得這次按鍵。
  • 素材 0.2 秒按下：先保存，再接招。 此時可預約但尚不可接招，因此先存入 Buffer，回傳 Buffered，畫面仍播放第一招。再經過 0.3 遊戲秒抵達 Enable 時，這筆輸入尚未超過 0.5 秒期限；角色會嘗試消耗它並開始下一招，玩家不必再按一次。原本那次呼叫的回傳值仍是 Buffered，後續接招是另一個時點的處理。
  • 素材 0.6 秒按下：立即嘗試接招。 此時兩個條件都為 true；SubmitCommand() 先寫入 Buffer，隨即呼叫 ConsumeCommandBuffer()。播放成功就回傳 Started，不用先等滿 0.5 秒，也不用等第一招完整播完。
  • 素材恰好 0.8 秒按下：已經太晚。 Disable 不包含在窗口內，不能再預約或接招，也不會保留到回到 Idle 後自動出招。

若把第二個案例改成 PlayRate＝0.5，仍在素材 0.2 秒按下，走到素材 0.5 秒的 Enable 就要花 (0.5 − 0.2) ÷ 0.5＝0.6 遊戲秒。Buffer 只保留 0.5 遊戲秒，因此抵達 Enable 時，雖然 CanLink() 已為 true，舊輸入卻已逾期，接不出下一招。若玩家之後在 Enable 到 Disable 之間重新輸入合法指令，仍可立即嘗試接招。

接出下一招需要同時滿足「允許交接、有尚未逾期的合法輸入、下一招可成功播放」。 單看 CanLink() 為 true 不代表一定會接招；另外，Debug 顯示的 Link 階段從 DamageEnd 就開始，也不等於已抵達 Enable。

設計幀：動畫播到哪裡？ 設計幀是動畫時間軸上的位置刻度。本週用「素材每 1 秒分成 60 格」來表示位置，所以 Debug Frame＝素材位置秒數 × 60。例如，素材的 0.2 秒位置就是設計幀 12（0.2 × 60＝12）。以下的素材位置與間距都是說明用的假設數字，不代表專案中 Notify 的實際設定。

假設傷害 Notify 放在素材的 0.2 秒位置，「傷害從設計幀 12 開始」就是指動畫播到這個位置時，開始產生傷害。Debug 若讀到素材位置 0.205 秒，就會顯示設計幀 12.3；因此這個數字可以有小數。

FPS 則表示電腦每秒顯示多少張畫面。設計幀的 60 是位置換算的基準，不代表目前 FPS，也不要求動畫原始素材一定以 60 FPS 製作。看到 Frame＝12，要讀成「目前播到素材的第 12 格位置」，不要讀成「目前只有 12 FPS」或「起招後已顯示 12 張畫面」。

播放速度：走到同一個位置要花多久？ PlayRate＝1 是正常速度，PlayRate＝0.5 是半速。假設從動畫開頭持續播放，傷害 Notify 仍放在素材的 0.2 秒位置：

播放速度 傷害 Notify 的位置 從動畫開頭播到該位置所需的遊戲時間
PlayRate＝1（正常速度） 素材 0.2 秒／設計幀 12 0.2 ÷ 1＝0.2 秒
PlayRate＝0.5（半速） 素材 0.2 秒／設計幀 12 0.2 ÷ 0.5＝0.4 秒

半速播放時，角色要花兩倍時間才揮到同一個姿勢。Notify 仍在原本的位置，只是比較晚才播到它。

Buffer 期限：這次輸入最多能等多久？ 攻擊途中，玩家在 CanPreorder() 為真的區間內按下下一招，還要通過角色狀態與合法後續招式檢查，這筆輸入才會被接受並存入 Buffer。Buffer 保存的是攻擊語意與按下時的方向，從「這筆輸入被接受的當下」開始計時，最多保留 0.5 遊戲秒；不是從 Preorder 窗口開啟時開始算，也不是所有按鍵都會被保存。

CanPreorder() 回答「現在的動畫位置允不允許預約」，Buffer 期限回答「已接受的這筆輸入還能等多久」。兩者使用不同的時間基準：前者看素材位置，後者看經過的遊戲時間。動畫改成半速，Buffer 的期限仍是 0.5 遊戲秒，不會自動延長成 1 秒。

對照程式定義。 以下節錄位於 Source/TndaFighter/Fighting/，可依檔名與函式名稱找到原始碼：

// FightingCommandLink.cpp：FFightingAttackTiming::CanPreorder()
bool FFightingAttackTiming::CanPreorder(float Position) const
{
    return IsValid() && Position >= Preorder && Position < Disable;
}

// FightingCommandLink.cpp：FFightingAttackTiming::CanLink()
bool FFightingAttackTiming::CanLink(float Position) const
{
    return IsValid() && Position >= Enable && Position < Disable;
}

// FightingCommandLink.h：FFightingCommandBuffer 的期限常數
static constexpr double Lifetime = 0.5;

// FightingCharacter.cpp：SubmitCommand() 通過窗口與合法候選檢查後
CommandBuffer.Submit(Command, Directions, GetWorld()->GetTimeSeconds(), true);

// FightingCommandLink.cpp：FFightingCommandBuffer::Submit() 保存受理時間
SubmittedAt = Now;

// FightingCommandLink.cpp：FFightingCommandBuffer::IsPending()
bool FFightingCommandBuffer::IsPending(double Now) const
{
    return !Attack.IsNone() && FMath::IsFinite(Now) && Now >= SubmittedAt && Now < SubmittedAt + Lifetime;
}

Position 是目前的素材位置；Now 是傳入的世界遊戲時間；SubmittedAt 是這筆輸入的受理時間。IsPending() 除了檢查有沒有輸入及時間是否合法，還要求 Now < SubmittedAt + Lifetime：例如在遊戲時間 10.0 秒受理，到了 10.5 秒就已逾期。

0.5 秒是保留上限，不保證每筆輸入都等滿這段時間：Enable 已開時可立即嘗試接招；取用輸入時就會清除預約，再重新選招並嘗試播放。到達 Disable、攻擊中斷或結束，也會清除剩餘預約。新的合法輸入會覆寫舊預約，並從新輸入受理時重新計算 0.5 秒；無效輸入不會延長期限。

比較等待時間、接招窗口與輸入期限。 假設玩家在素材 0.2 秒的位置輸入下一招並存入 Buffer，Enable 位於素材 0.5 秒，Disable 位於素材 0.8 秒。這組數字是教學算例；Buffer 的期限由 FFightingCommandBuffer::Lifetime = 0.5 定義。

比較項目 正常速度 PlayRate=1 半速 PlayRate=0.5
輸入後等到 Enable (0.5 − 0.2) ÷ 1＝0.3 遊戲秒 (0.5 − 0.2) ÷ 0.5＝0.6 遊戲秒
Buffer 期限 0.5 遊戲秒 0.5 遊戲秒
這筆提前輸入的結果 抵達 Enable 時仍有效，可嘗試接招 抵達 Enable 前已逾期
Enable 到 Disable 的窗口長度 (0.8 − 0.5) ÷ 1＝0.3 遊戲秒 (0.8 − 0.5) ÷ 0.5＝0.6 遊戲秒

以上算例假設播放速度固定、動畫持續播放，沒有暫停或時間倍率變化，也沒有新輸入覆寫或其他清除 Buffer 的事件。在這些條件下，用「素材位置的間距 ÷ PlayRate」就能估算要經過多少遊戲時間。

半速把這段接招窗口從 0.3 遊戲秒拉長到 0.6 遊戲秒，在窗口內輸入時有較多時間完成操作；合法輸入被接受後便立即嘗試接招。若在 Enable 前提早輸入，則要先等到窗口開啟，這段等待也會因半速而變長，可能超過 Buffer 的 0.5 秒期限。

放慢後是否比較好接，取決於輸入時機：接近 Enable 或在窗口內輸入可能較容易掌握；太早預約則可能在開窗前逾期。 比較兩種速度時，要同時看「輸入後等多久」與「窗口持續多久」。

課前預習 2｜輸入怎麼從預約變成下一招？

資料與預約。 _DataTable/CommandTable.csv 的 Link 欄位設定目前招式可以銜接的後續招式。例如，ID 1 的 Link 填入 3，表示使用第 1 號招式時，可以透過符合條件的輸入接出第 3 號招式。本週教材的初始設定只有這一組接招關係。

玩家在可預約區間內提前輸入下一招，通過角色狀態與合法後續招式檢查後，系統會將這次輸入存進 Buffer。例如，玩家按下 I 提出 Y 攻擊時，Buffer 會保存以下內容：

保存內容 用途
攻擊語意 Y 記錄玩家這次提出的攻擊輸入
按下攻擊時的方向 保存當時相對於對手的方向，供接招時查找符合條件的招式
受理時間 從這個時點開始計算 0.5 遊戲秒的有效期限

「方向快照」就是把按下攻擊當時的方向記下來。例如，某筆被接受的輸入包含朝向對手的方向 6，之後即使玩家放開方向鍵，這筆預約仍保留當時的 6。接招窗口開啟時，系統會用保存的攻擊與方向，在目前招式允許的後續招式中重新查找，並嘗試播放下一招。

每個角色各自有一個 Buffer，最多保存一筆輸入。新的合法輸入會取代原本那筆，並從新輸入的受理時間重新計算 0.5 秒。以下用假設的遊戲時間說明；假設期間預約窗口持續開啟，且預約尚未被消耗或清除：

時間與情況 Buffer 的內容與期限
10.0 秒接受一筆合法輸入 保存這筆輸入，到 10.5 秒時逾期
10.2 秒又接受一筆合法輸入 改存新輸入，到 10.7 秒時逾期
若 10.2 秒收到的是無效輸入 保留原本那筆輸入，仍在 10.5 秒時逾期

表格最後兩列是兩種不同情況。實際接招時，Buffer 內的輸入還必須在有效期限內；接招、到達 Disable 或攻擊中斷等事件也會提前清除預約。

輸入路徑：按下 I，先把 Y 存成預約。 延續前面的例子：角色正在播放第 1 號招式，Link 設為 3。玩家在 Preorder 已開、Enable 尚未開啟時按下 I，提出 Y 攻擊。這次輸入會依序經過以下處理；原始碼路徑均以 Source/TndaFighter/ 為起點。

  1. 角色收到輸入。 Fighting/FightingCharacter.cpp 的 SubmitCommand() 收到攻擊語意 Y 與按下當時的方向，更新目前攻擊狀態，再用 IsCommandPreorderOpen() 確認角色現在可以接受預約。
  2. 查找符合輸入的後續招式。 DataTable/TndaCommandReader.cpp 的 TrySelectLinkedCommand() 將攻擊、方向與目前的 Link 交給 SelectCommand()。本例的 Link 只有 3，因此會檢查第 3 號招式是否符合這次輸入；有多個合法候選時，依資料表整理好的排序選出第一個符合者。
  3. 保存這次輸入。 通過檢查後，呼叫 Fighting/FightingCommandLink.cpp 的 FFightingCommandBuffer::Submit()，保存 Y、方向與受理時間，並開始計算 0.5 遊戲秒期限。
  4. 回報已預約。 此時 Enable 尚未開啟，SubmitCommand() 回傳 Buffered。畫面繼續播放第 1 號招式，Buffer 留著這筆 Y 輸入，等待接招時機。

若預約窗口已關閉，或找不到符合輸入的合法後續招式，SubmitCommand() 會回傳 Rejected。若玩家按下 I 時已在 Enable 到 Disable 的接招區間，保存輸入後就會立即呼叫 ConsumeCommandBuffer() 嘗試接招；下一招播放成功回傳 Started，失敗則回傳 Rejected。

交接路徑：播到 Enable，把預約的 Y 接出來。 接著看剛才回傳 Buffered 的情況。假設輸入被接受後，過了 0.3 遊戲秒，第一招播放到 Enable；這筆預約仍在 0.5 秒期限內，角色狀態也允許接招。

  1. 動畫通知角色檢查接招。 Enable Notify 觸發後，Fighting/FightingCommandLinkNotify.cpp 的 UFightingCommandLinkEnableNotify::Notify() 經由 DispatchLinkNotify() 呼叫角色的 HandleCommandLinkNotify()。角色確認通知來自目前這次攻擊，並更新攻擊狀態與素材位置。
  2. 確認窗口與預約都有效。 角色透過 IsCommandLinkOpen() 檢查接招窗口，並在有預約時呼叫 ConsumeCommandBuffer()。這個函式再次確認 Buffer 尚未逾期，而且此刻仍允許接招。
  3. 取出輸入，重新選招。 ConsumeCommandBuffer() 取出保存的 Y 與方向，清除這筆已取用的預約，再呼叫 TrySelectLinkedCommand()。本例會重新確認第 3 號招式符合條件，並取得它目前的招式資料。
  4. 開始下一招並完成交接。 選招成功後，呼叫 Fighting/FightingCharacter.cpp 的 StartAttack(..., true)；其中 true 表示這次是從目前攻擊銜接下一招。函式檢查下一招資料並嘗試播放 Montage，播放成功後讓第一招依自身 Blend Out 設定淡出，清除舊的命中紀錄，並把目前攻擊更新為第 3 號招式。

玩家看到的過程是「按下 I → 第一招繼續播放 → 到達接招窗口 → 第 3 號招式開始」。若等待期間預約已逾期、角色狀態改變，或下一招選取／播放失敗，這次預約就無法完成接招。角色的 UpdateAttack() 也會持續檢查窗口與預約，讓符合條件的交接能在更新時處理。

招式資料在什麼時候讀取？ 以第 1 號招式接第 3 號招式為例，角色會在起招與接招時分別取得需要的資料：

  1. 第 1 招開始時，保存這次攻擊的資料。 StartAttack() 將選出的第 1 號招式資料存入角色的 CurrentAttack，其中包含 Link = 3。這就是「起招時的副本」：角色保存了一份這次攻擊要使用的資料，後續透過 CurrentAttack.Link 判斷允許銜接哪些招式。
  2. 玩家提前按下 I 時，先確認能否預約。 SubmitCommand() 使用保存的 CurrentAttack.Link 查找合法後續。符合條件後，Buffer 記住這次 Y 輸入、方向與受理時間。
  3. 接招窗口開啟時，再取得第 3 招的資料。 ConsumeCommandBuffer() 取出預約的 Y 與方向，將它們連同 CurrentAttack.Link 交給 TrySelectLinkedCommand()。查詢成功後，取得第 3 號招式的資料，例如要播放的 Montage 與 PlayRate，再交給 StartAttack(..., true) 開始播放。

因此，「起招時保存副本」指的是第 1 招開始時，角色記住這次攻擊允許接出的招式 ID；「消耗時重新查」指的是使用預約輸入接招時，再查詢符合條件的第 3 招資料。下一招成功開始後，CurrentAttack 會更新為第 3 招的資料，後續接招也改用第 3 招自己的 Link。

預約何時清除？ 嘗試接招時，先取出輸入並清除 Buffer，再重新選招與播放；即使後續選招或播放失敗，這筆輸入也已取用。到達 Disable、輸入逾期、攻擊中斷或完整結束時，也會清除剩餘預約。Recovery 期間收到的攻擊輸入會被拒絕；回到 Idle 後，玩家可重新輸入出招。教材的 X→Y 接招條件允許第一招揮空，只要輸入、窗口與播放條件都成立，就能接出 Y。
