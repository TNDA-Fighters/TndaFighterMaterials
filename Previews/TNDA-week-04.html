本週目標

  • 找到角色移動與場地牆的碰撞設定，做出看得見但可穿過的指定牆段。
  • 依序調整 C++ 與 Blueprint 的膠囊半徑，用遊戲中的數值及碰牆位置解釋結果。
  • 分清角色碰牆、鏡頭碰牆與雙方最大距離三種限制。

課前準備

使用本週提供的 TndaFighter 教材，確認能編譯並開啟 /Game/Fighting/stage1，按 Play 後可用 W／A／S／D 操作 1P。PIE（Play In Editor）就是在編輯器內執行遊戲。

本週教材以 week-04（680b61ab）為基準，已包含 CPU 膠囊初始化修正：1P 與 CPU 的建構子都使用 InitCapsuleSize(35.0f, 90.0f)。若手上的 CPU 程式仍是 SetCapsuleSize()，先向助教核對教材版本。

準備能編輯 C++ 的 IDE。兩項練習都會修改教材設定，完成後還原。課堂以遠端分享桌面、實機操作與口頭說明驗收，請先熟悉重現成果的方式。

課前預習

課前預習 1｜從移動輸入找到角色碰撞與場地牆

先分清外觀、碰撞形狀與移動

Actor 是放進關卡或在遊戲中生成的物件；Component 是物件上負責某種工作的元件。本週先辨認三個元件：

對象 元件 本週要看什麼
角色外觀 Skeletal Mesh，也就是有骨架與動畫的角色模型 身體看起來在哪裡、動作如何播放。
角色碰撞 Capsule Component，膠囊形碰撞元件 角色移動時，用什麼形狀檢查能否通過。
場地牆 StaticMeshComponent，靜態模型元件 牆的模型及碰撞回應。

CharacterMovement 是 ACharacter 使用的移動元件。本週的地面移動以 Capsule 作為主要碰撞形狀；角色衣服、手臂或腳的外觀不等於這個膠囊的邊緣。

「自己是哪一類」與「遇到別人怎麼辦」

Object Type 是物件在碰撞系統中的類型。本教材的角色 Capsule 是 Pawn，場地牆是 WorldStatic。CPU 也是 Pawn，這個類型不表示一定由真人控制。

Collision Response 是遇到指定 Channel 時的回應；Channel 可以先理解成碰撞查詢使用的分類。Block 表示阻擋，Overlap 表示可重疊，Ignore 表示忽略這種互動。Overlap 要發出事件還需要相關事件設定，選成 Overlap 不等於自動執行一段程式。

Collision Presets 把常用設定組成一個預設組合。牆原本使用 BlockAll，對 Pawn 為 Block；角色 Capsule 對 WorldStatic 也為 Block。判斷兩個物件是否互相阻擋時，要一起看雙方的類型與回應。碰撞設定參考

沿著原始碼走到元件設定

以下路徑都從 TndaFighter 專案根目錄算起。這條追蹤從收到移動值開始，到角色與牆的設定為止；這次不展開引擎內部如何逐步解算碰撞，也先略過 4／6 分類與推擠細節。

  1. 開啟 Source/TndaFighter/Fighting/FightingPlayerCharacter.cpp，找到 AFightingPlayerCharacter::Move()。它從輸入值取出 FVector2D；X 是左右，Y 是前後，再呼叫 DoMove(MovementVector.X, MovementVector.Y)。
  2. 同檔的 AFightingPlayerCharacter::DoMove() 以攝影機的水平朝向換算世界方向。世界方向是相對關卡座標的方向；攝影機轉了，畫面上的右方不一定仍是世界 X 正方向。程式最後分別呼叫 AddMovementInput(ForwardDirection, Forward) 與 AddMovementInput(RightDirection, Right)。
  3. AddMovementInput() 提供的是方向與輸入比例，不是保證完成的位移。Character 會由引擎的移動流程處理這份輸入；這是引擎接手的邊界，不是 DoMove() 裡再直接呼叫一個「碰牆函式」。API 說明
  4. 對照 Source/TndaFighter/Fighting/FightingPlayerCharacter.h 的 AFightingPlayerCharacter : public AFightingCharacter，再看同目錄 FightingCharacter.h 的 AFightingCharacter : public ACharacter。冒號後的 public 表示公開繼承；循著這條關係，可找到角色沿用的 Capsule 與 CharacterMovement。
  5. 回到玩家建構子 AFightingPlayerCharacter::AFightingPlayerCharacter()，找到 GetCapsuleComponent()->InitCapsuleSize(35.0f, 90.0f)。在 /Game/Fighting/Blueprints/BP_FightingPlayerCharacter 對照繼承的 Capsule；最後在 stage1 找到 ArenaBoundary_Wall_00 的 StaticMeshComponent，比較雙方的 Collision 設定。

測試時還有另一條距離規則

本教材的 BP_FightingCamera 將 1P 與 CPU 的最大水平間距設為 650 cm。即使前方沒有牆，1P 遠離 CPU 仍可能被這條規則限制；它與場地牆分開運作。練習時讓雙方都從指定牆附近的場內開始，避免還沒碰牆就先到達最大間距。教材沒有把場外出生角色自動送回場內的功能。

課前預習 2｜角色還沒貼到牆，為什麼就停住？

膠囊半徑與半高

Capsule Radius 是膠囊在水平面的半徑；Capsule Half Height 是從中心到頂端或底端的距離，包含圓頂。本題單位皆為公分（cm）。半徑 35 代表水平直徑 70；半高 90 代表總高度 180。這些數字描述碰撞形狀，不是 Mesh 的身高或肩寬。Capsule 元件參考

在牆段中央、角色與牆正常阻擋、縮放不變的條件下，膠囊外緣先接觸牆面，角色中心才會停下。因此實際半徑越大，中心通常在離牆較遠處停止；只改 Capsule Radius 不會把角色 Mesh 一起放大。比較時要看角色中心與同一面牆的距離，不能只看某個動畫姿勢的手或腳。

從兩個建構子追到各自的 Blueprint

建構子是建立物件時提供初始設定的 C++ 函式，名稱與類別相同。GetCapsuleComponent() 取得此角色的膠囊元件；-> 表示透過取得的元件呼叫功能。35.0f、90.0f 是帶小數的數值寫法，f 表示 float 型別。

  1. 在 Source/TndaFighter/Fighting/FightingPlayerCharacter.cpp 找到 AFightingPlayerCharacter::AFightingPlayerCharacter()；在同目錄 FightingCpuCharacter.cpp 找到 AFightingCpuCharacter::AFightingCpuCharacter()。

  2. 本週提供的修正版中，兩個建構子都呼叫下列初始化。第一個參數是半徑，第二個是半高：

    GetCapsuleComponent()->InitCapsuleSize(35.0f, 90.0f);

  3. 對照 FightingPlayerCharacter.h、FightingCpuCharacter.h 與 FightingCharacter.h，確認兩條繼承關係都是「各自的角色類別 → AFightingCharacter → ACharacter」。兩名角色共用父類能力，仍各有自己的元件與設定。

  4. 在 /Game/Fighting/Blueprints/BP_FightingPlayerCharacter 與 /Game/Fighting/Blueprints/BP_FightingCpuCharacter 找到繼承的 Capsule，對照 Shape 的 Capsule Radius、Capsule Half Height。本題調整的是這個元件，不是旁邊的 Mesh。

  5. Play 後再看遊戲中生成的兩名角色。PIE 執行個體是這次遊戲裡的角色物件，它的 Capsule 值才是當次測試採用的碰撞尺寸。

課前實作練習

課前實作練習 1｜讓一段看得見的牆可以穿過

只把 /Game/Fighting/stage1 中 ArenaBoundary_Wall_00 對 Pawn 的回應改為 Ignore，做出「牆仍看得見，1P 可以穿過它，相鄰牆段仍會擋住角色」的場景。

保留這段牆的 Mesh、Transform、WorldStatic 類型及其他 Channel 回應，也不修改角色 Capsule。可調整既有 PlayerStart 與 CpuStart 的水平位置，讓雙方從牆附近的場內開始；測試時雙方間距須小於 650 cm。

先預測修改後的通行情況。課堂上分享桌面，直接展示指定牆可穿過、相鄰牆仍會阻擋，並指出改動的回應欄位。依預習 1 找到接收輸入與送出移動意圖的檔案、函式，口頭說明為什麼牆仍看得見，阻擋結果卻不同。

課前實作練習 2｜先改 C++、再改 Blueprint，膠囊半徑最後以誰為準？

對 1P 與 CPU 依序完成以下三個階段，讓每個階段的設定都用於新一輪 PIE，並確認膠囊大小與碰牆結果。階段之間保留前一步設定：

  1. 兩個 C++ 建構子的半徑由 35 改為 50，確認新編譯結果已載入。
  2. 兩個 Blueprint 的 Capsule Radius 由 50 改為 20，保存為下一輪遊戲使用的設定。
  3. 保留 Blueprint 的 20，只把 C++ 半徑由 50 改為 80，再次確認新編譯結果已載入。

半高維持 90，Mesh、縮放與牆的設定保持不變；測試避開牆角、另一名角色接觸及最大距離限制。C++ 變更採完整建置後重新載入，不使用 Live Coding。

課堂上遠端分享桌面，直接展示 C++ 參數、BP Capsule 與 PIE 畫面，並口頭說明：「為什麼第 1 步 C++ 35 → 50 會改變角色半徑，第 3 步 C++ 50 → 80 卻沒有？」

官方參考資料

  • Epic Games：Collision Response Reference：對照 Object Type、Collision Enabled、Presets 與各 Channel 的回應。
  • Epic Games：APawn::AddMovementInput：確認世界方向與輸入比例的用途。
  • Epic Games：UCapsuleComponent：查看半徑、半高與 InitCapsuleSize()。
