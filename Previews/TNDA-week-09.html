課前預習 2｜ST_FightingCpu 實現了哪些功能？它怎麼和 C++ 與 Blueprint 串接？

先看正式樹在做什麼

開啟 /Game/Fighting/AI/ST_FightingCpu。它使用 StateTreeAIComponentSchema，Actor Context 是 FightingCpuCharacter。Context 是執行這棵樹的 CPU，不是玩家。

狀態 現有工作 完成後的去向
Approach 主動接近玩家 回 Root 重新選擇
Attack 執行一組攻擊，必要時預約一次合法後續招式 Wait
DefensePrepare 等待防禦準備完成 成功去 Defense，失敗去 Wait
Defense 維持本次攻擊序列的防禦流程 Wait
Hold 不主動接近，等行動資格或判斷改變 Root
Wait 一組行動後的決策等待 Root；新的合格防禦威脅可以提早交回決策

「一組攻擊」可能是單招，也可能是既有 X→Y；最後一招完整收尾後，Attack Task 才完成。本週課堂說的「第二波」，是再起一組新的攻擊，不是把 X→Y 改成三段連招。

根參數是整棵正式樹的公開設定：

參數 week-09 基準 用途
EnterDistance／ExitDistance 100／120 cm 進入／退出近戰的水平中心距離
ApproachSpeed 400 cm/s 接近時的速度上限
WaitDuration 0.8 秒 一組行動後等待
DefenseDistance 120 cm 觀察新攻擊時可嘗試防禦的距離
DefenseReactionTime 0.2 秒 抽中防禦後的準備時間
DefenseChance 0.5 每個新攻擊序列一次的防禦機率

100～120 cm 是遲滯區：從遠處進入時，要到 100 cm 內才算近戰；已在近戰時，要超過 120 cm 才退出。中間保留原判斷，避免在同一個距離邊界反覆切換。這是決策距離，並不保證拳腳一定打得到。

先看全貌：先啟動，再反覆決策與動作

把全貌拆成兩張泳道循序圖，分別對應下面兩條追蹤路徑。每欄是一個職責，由上往下讀；箭頭先寫「做什麼」，下一行附程式閱讀入口（Entry）。 先看圖，再讀下面的三站主線；完整檔案對照與條件細節放在各路徑的收合區，想追程式時再展開。

圖一｜啟動：先把對局準備好，再讓 CPU 開始思考

這張圖只回答「樹怎麼開始執行」。CPU 生成時，引擎就可能建立控制器並讓它接管角色；接管角色與開始執行 AI 是兩件事，要等 GameMode 把對局準備好，Controller 才能啟動樹。角色與控制器合併在同一欄，詳細分工見追蹤路徑一。

圖二｜執行：看現在的情況 → 選要做的事 → 交給角色執行

這張圖只回答「樹開始後，判斷怎麼變成動作」。C++ 觀察欄與動作欄按職責區分，不代表兩個獨立物件。Evaluator 算出目前情況，StateTree 選狀態，Task 再請角色做事。 接近與攻擊各有自己的 Task；Task 回報結束後，StateTree 才依該狀態的轉移設定接著走。

追蹤路徑一：從生成 CPU，追到樹開始執行

CPU 已經出現在場上，AI 就開始了嗎？ 要等對局準備好，控制器才啟動 StateTree。

  1. 生出角色。 GameMode 生成 CPU，引擎安排控制器接管。
    Entry：FinishRestartPlayer() → OnPossess()
  2. 準備好對局。 雙方配對、朝向與相機設定完成後，通知 CPU 開場已就緒。
    Entry：NotifyMatchReady()
  3. 開始執行樹。 控制器確認對局已就緒、AI 已開啟、測試模式沒有接手，再啟動樹。
    Entry：RefreshAIControl() → StartLogic()

用一個情況理解： CPU 已經生成、控制器也接管了，但 GameMode 還沒通知開場完成。此時 CPU 會先等著，直到開場就緒且其他檢查通過，才開始執行樹。這就是「先確認對局準備好了，而且現在輪得到 AI 操作 CPU」。

停一下，確認自己懂了： NotifyMatchReady() 與 StartLogic()，哪個是通知開場完成，哪個才是真的啟動樹？

想追更深：完整程式定位、啟動條件與例外
圖一步驟 關鍵程式碼 Entry／設定入口
① 生成 CPU FightingGameMode.cpp：AFightingGameMode::FinishRestartPlayer()，從 SpawnActor<AFightingCpuCharacter>(CpuClass, ...) 讀起；BP_FightingGameMode 的 CpuClass 決定生成哪個角色
② 控制器接管 FightingCpuCharacter.cpp：建構子的 AIControllerClass、AutoPossessAI；接著看 FightingCpuController.cpp 的 AFightingCpuController::OnPossess()。中間由引擎生命週期串接
③ 通知開場完成 FightingGameMode.cpp：FinishRestartPlayer() 結尾的 CpuCharacter->NotifyMatchReady()；宣告在 FightingCpuCharacter.h
④ 每幀詢問 FightingCpuCharacter.cpp：AFightingCpuCharacter::Tick() → FightingCpuController.cpp：AFightingCpuController::RefreshAIControl()
⑤ 檢查能否運作 FightingCpuController.cpp：AFightingCpuController::GetAIControlBlockReason()
⑥ 啟動樹 同檔 RefreshAIControl() 的 StateTree->StartLogic()；元件由 AFightingCpuController 建構子建立，BP_FightingCpuController 的 StateTree 元件以 StateTreeRef 引用 /Game/Fighting/AI/ST_FightingCpu

這條路徑要回答：CPU 已經出現在場上了，為什麼還要等一下才能讓 AI 運作？ 以下 C++ 檔案都在 Source/TndaFighter/Fighting/，Blueprint 都在 /Game/Fighting/Blueprints/。依圖一的 ①～⑥ 順序讀：

  1. GameMode 先生成 CPU。 看 BP_FightingGameMode 的 CpuClass，它指定 BP_FightingCpuCharacter。再開 FightingGameMode.cpp 的 AFightingGameMode::FinishRestartPlayer()，找到 SpawnActor<AFightingCpuCharacter>()；這裡把設定中的角色生成到 CPU 出生點。
  2. 引擎替 CPU 安排控制器，但先不啟動樹。 BP_FightingCpuCharacter 的 AIControllerClass 指定 BP_FightingCpuController，角色的 AutoPossessAI 允許生成後由 AI 接管。接著看 FightingCpuController.cpp：建構子建立 UStateTreeAIComponent、交給 BrainComponent，並關閉自動啟動；OnPossess() 則安排「CPU 角色 → StateTree → Movement」的每幀執行順序。Controller 的 StateTree 元件以 StateTreeRef 選用 ST_FightingCpu。引擎依角色設定呼叫 OnPossess() 是生命週期串接；GameMode 沒有直接呼叫它。
  3. GameMode 把對局準備好，再通知 CPU。 回到 FinishRestartPlayer() 往下讀：雙方用 SetOpponent() 記住彼此，設定朝向與相機，全部成功後才呼叫 NotifyMatchReady()。這表示 CPU 已有對手、開場也已完成。
  4. CPU 每幀問控制器：「現在可以讓 AI 操作我嗎？」 開 FightingCpuCharacter.cpp 的 AFightingCpuCharacter::Tick()，沿 CpuController->RefreshAIControl() 進入 FightingCpuController.cpp。
  5. 控制器逐項檢查，有問題就先不讓 AI 操作。 在 RefreshAIControl() 先追 GetAIControlBlockReason()：CPU 是否有效且已收到開場完成通知？雙方是否互相把對方設為對手？這個 Controller 是否確實控制這個 CPU，且三者都在同一個 World？再看 AI 是否被手動關閉，以及測試移動模式是否正在接手。分別可能得到 NotReady、ManualOff、TestMovement；沒有阻擋原因才繼續。若樹原本正在執行，現在卻被擋住，會透過 ReleaseAIControl() 停樹並清理 AI 輸入。
  6. 檢查通過，才啟動一次。 回到 RefreshAIControl() 的 if (!bOwnsAIControl && HasActorBegunPlay())，這裡才呼叫 StateTree->StartLogic()。樹已在執行時，下一幀不會重啟，因此能保留目前 Task、距離判斷與等待進度。

原本的「核對控制權與就緒條件」，就是上面第 ⑤ 步：先確認對局準備好了，而且現在輪得到 AI 操作 CPU。 至於要接近、出招還是等待，是樹啟動後才處理的事。因此要讓 CPU 使用新樹，除了建立資產，也要把 Controller 的 StateTreeRef 指向它。

追蹤路徑二：從「該做什麼」，追到角色真的移動或出招

StateTree 選到 Approach，是誰真的讓 CPU 走近玩家？ Move Task 請 CPU 送出移動輸入。

  1. 看現在的情況。 Evaluator 算距離與行動資格，寫出「現在該接近嗎？」等結果。
    Entry：FFightingCpuEvaluator::Tick()
  2. 選要做的事。 StateTree 用進入條件選狀態，選到 Approach 就執行 Move Task。
    Entry：ST_FightingCpu 的 Enter Conditions → FFightingCpuMoveTask::EnterState()
  3. 動作做到該停，再交回樹選擇。 Move Task 請 CPU 接近；接近判斷改變時回報完成，由轉移回 Root。
    Entry：ApplyAIApproach() → AddMovementInput()；完成看 FFightingCpuMoveTask::Tick()

跟著走一圈： CPU 還在遠處、目前可以行動，也沒有防禦流程擋住接近 → 選到 Approach → Move Task 每幀請角色靠近 → 到達近戰範圍後，不再需要接近 → Task 回報完成 → 回 Root 重選。

攻擊也沿用這個分工： 選到 Attack 後，Attack Task 呼叫 TryStartAIAttack()；CPU 選招，再經 SubmitCommand() 交給共用戰鬥流程。完整起手、後續招式與等待規則放在下方。

這條路徑要回答：樹裡選到 Approach 或 Attack 之後，究竟是哪段程式讓角色動起來？ 先開 Source/TndaFighter/Fighting/FightingCpuStateTree.cpp，再依呼叫進入同目錄的 FightingCpuCharacter.cpp 與 FightingCharacter.cpp。依圖二的 ①～⑤ 順序讀：

  1. Evaluator 先看目前情況，寫出判斷結果。 FFightingCpuEvaluator::TreeStart() 會初始化並立即呼叫 Tick()，讓第一次選狀態時就有資料。之後每幀的 Tick() 先檢查參數與 CPU 能否行動，再算雙方水平距離、更新防禦判斷，最後寫出 bShouldApproach、bShouldAttack 等結果。你可以把它們讀成「現在該接近嗎？」與「現在該攻擊，或繼續追蹤這組攻擊嗎？」。
  2. StateTree 看這些結果，挑出狀態。 切回 /Game/Fighting/AI/ST_FightingCpu，看 Root 下各狀態的 Enter Conditions → Bool Compare，並查看條件欄位的 Binding。Binding 就是「這個欄位要從哪裡拿資料」；根參數提供距離、速度等設定，Evaluator 輸出則提供本幀判斷。沿 Approach 或 Attack 的條件追到對應輸出，就能知道為什麼會選到它。
  3. 進入狀態後，Task 才請角色執行動作。 在 FightingCpuStateTree.cpp 分別追兩條支線：
    • 接近： FFightingCpuMoveTask::EnterState()／Tick() → FightingCpuCharacter.cpp 的 AFightingCpuCharacter::ApplyAIApproach(ApproachSpeed) → AddMovementInput(Direction)。Task 把樹提供的速度交給角色，角色設定速度上限並送出朝對手的移動輸入；離開時，FFightingCpuMoveTask::ExitState() 呼叫 StopAIApproach()，撤回主動追逐。
    • 攻擊： FFightingCpuAttackTask::EnterState() → AFightingCpuCharacter::TryStartAIAttack()。CPU 用 UTndaCommandReader::GetCommandCandidates() 取得合法候選，抽出一招，把它的攻擊語意與方向交給 FightingCharacter.cpp 的 AFightingCharacter::SubmitCommand()。這個共用入口再次檢查選招與播放資格，成功才進 StartAttack()，由 Montage_Play() 播放攻擊動畫。
  4. Task 持續查看事情做完了沒。 回到各 Task 的 Tick()：回傳 Running 就繼續留在任務；Succeeded／Failed 則把結果交回樹。例如 Move Task 發現接近判斷改變，就回報完成；Attack Task 會等這組攻擊完整收尾，期間透過 TrySubmitAIFollowup() 最多嘗試一次合法後續。起手沒有成功時，Attack Task 也會在下一次 Tick 回報完成，交由樹安排等待。
  5. StateTree 決定做完後去哪裡。 回資產看目前狀態的 Transitions：Approach 完成後回 Root 重選；Attack 完成後進 Wait；Wait 的 Task 在等待到期，或遇到新的合格防禦威脅時回報完成，再由轉移回 Root。Task 負責回報結果，下一站寫在資產的轉移設定中。

這張圖只展開「新的一組攻擊如何起手」；後續招式可能由共用流程回傳 Buffered，代表已接受預約，等待合法交接時機。Attack Task 的完成判斷仍看整組攻擊是否收尾。

FightingCpuStateTree.h 的 Context 欄位接收執行這棵樹的 CPU；Input 從根參數或 Evaluator 接收資料；Output 提供計算結果。這些欄位的 C++ 初值常是 0／false，正式執行時的值還要看資產 Binding，不能只讀宣告就當成遊戲中的值。

課前實作練習 1｜StateTree 導讀的三題開放問答

請根據導讀回答以下三題。每題提出自己的理由，指出對應的導讀章節或影片時間點，並說出一個你還不確定的地方。可以用短句或簡圖；課堂分享畫面並口頭說明，不必另外製作截圖或證明紀錄。

  1. 你會怎麼切狀態？ 選一種你熟悉的遊戲角色行為，用至少兩個 State 描述它。哪些工作適合放同一個 State 的不同 Task，哪些值得拆成另一個 State？說明你的取捨，以及一種你考慮過但沒有採用的分法。
  2. 你會從哪裡查起？ 假設你在 Chase State 中放了移動 Task 與 Duration 設為 1.2 秒的 Delay Task，希望 CPU 追逐玩家 1.2 秒後，才切換到 Rest State 休息。但實際執行時，Delay 尚未到期，StateTree 就從 Chase 切換到 Rest，CPU 也停止追逐。你會先看哪些設定、如何安排一次小實驗來分辨原因？如果反過來，Delay 已到期，StateTree 卻一直停留在 Chase、沒有切換到 Rest，你又會怎麼查？不必猜出唯一故障，重點是說明你的判斷依據。
  3. 你會把判斷放哪裡？ 假設敵人追逐時發現玩家走遠了，你想讓它繼續追、停下或改做別的事？你會如何分配 Evaluator、Condition、Transition 與 Task 的責任？說明這個設計對玩家的影響，以及你最想回看影片確認的概念。

課前實作練習 2｜自己重拉一棵新樹——有體力限制的追逐陪練

自行建立 /Game/Fighting/AI/ST_FightingCpuDrill，除了 Root，只能有 Chase、Rest 兩個狀態。CPU 每次最多追逐玩家 1.2 秒，接著停止追逐、休息 2 秒，休息結束才能再次追逐。CPU 全程不主動攻擊，也不防禦。

使用教材已提供的 Task，將新樹掛到 CPU Controller 執行；不要修改 C++，也不必新增體力條或體力數值系統。「有體力限制」在此以固定追逐／休息節奏表現。停止追逐指停止主動移動，原有煞車、碰撞與被推擠仍有效。

上課分享新樹與實機畫面：先拉開距離，展示 CPU 追逐、休息、再追逐；休息中移動玩家，確認 CPU 不會提早恢復追逐。請說明：哪個 Task 負責動作，哪個負責決定何時離開？若兩者回報完成的時機不同，這個 State 為什麼仍依你的計時規則轉移？ 展示後將 Controller 引用還原為 ST_FightingCpu，保留新樹。
