本週目標

課前預習

課前預習 1｜輸入當下的 6，如何選到分支終段

先分清三種「方向」

  • 實體按鍵：鍵盤上真的按下的鍵，例如 A、D、U、I。
  • 相對方向：程式拿來選招的數字。6 是朝對手前進，4 是遠離對手後退。它看的是對手在哪一邊，不看你按的是哪一顆鍵。
  • 攻擊語意：U 送出 X，I 送出 Y。選招時把相對方向和攻擊語意合在一起看，例如 6X、6Y。

站在對手左邊時，D 朝對手，所以 D 是 6、A 是 4。跳到對手右邊之後，朝對手的變成 A，所以 A 是 6、D 是 4。你一直按著「6」的意思沒變，手指要換一顆鍵。

方向在按下攻擊鍵的那一刻決定

  • 按下 U 或 I 時，程式讀取當下方向鍵的值，並依對手當下的位置判斷是 6、4 還是沒有方向。
  • 這組方向會跟著這次輸入一起送去選招。出招中先按下的輸入會存成「預約」，到接招那一刻再用同一組方向重新選一次，不會重新讀方向鍵。
  • 所以想接 6X，要在按下 U 的那一刻按著當時朝對手的那顆鍵。

選招的順序

  1. 先決定候選。 空檔起手時，候選是 Opener 為空白或 TRUE 的列；出招中，候選只有目前這一招 Link 列出的 ID。這條規則和上週相同。
  2. 資料表匯入時先排好順序。 程式把整張表排成固定順序：Priority 大的在前；Priority 相同時，Keys 有寫方向的列在前；再相同就比 ID，小的在前。
  3. 從排好的順序裡取第一個符合的列。 符合的意思是攻擊語意相同，而且 Keys 沒寫方向，或寫的方向在這次輸入的方向裡。

選招時程式只找第一個符合的列，所以「誰排在前面」在匯入時就已經決定好了。下面兩張圖分別畫出這兩個階段。

停一下，確認自己懂了： 如果把 ID 5 的 Priority 改成 1，ID 4 出招中按著 6 再按 U，會接出哪一招？為什麼？

參考答案

會接出 ID 5 連段三段。

  1. ID 4 出招中，候選只有 Link 裡的 ID 5 和 ID 2。
  2. 排序先比 Priority：ID 5 是 1，ID 2 是 0，所以 ID 5 排在前面。方向的比較只在 Priority 相同時才用到。
  3. 從前面開始找第一個符合的列：ID 5 的 Keys 是 X，沒寫方向，按任何方向都算符合，所以選到 ID 5。

改了之後，ID 4 出招中不管按不按 6，都只會接出 ID 5，右腳踢頭從這裡接不出來了。

課前預習 2｜越頂（6,Y）這招怎麼做出來的

先懂幾個名詞

  • 越頂：按著 6 再按 I，角色朝起跳當下的面向跳出一段固定的拋物線。它不打人，只用來換位置。
  • 無傷害招式：資料列的 Damage、Hitbox、Hurtboxes 都留空，Montage 上也沒有傷害判定的標記。越頂是目前唯一的無傷害招式。
  • 離地段：Montage 上的 Airborne Arc 標記。標記開始就起跳，標記結束就落地；這段期間角色的位置由程式逐幀放置，不靠動畫本身移動。
  • SPEC（規格）：開工前寫好的一份文件，寫清楚玩家會看到什麼、有哪些規則、怎樣才算完成。AI 和人都照它施工、照它驗收。

第一段：用 AI 把越頂從需求做到驗收

越頂是用 AI 協作開發出來的，走了五個步驟：提出需求 → 討論 → 產出 SPEC → 實作 SPEC → 驗收 SPEC。下面照順序模擬一次。

步驟 1｜提出需求

設計者先用玩家的角度講想要什麼，不講程式怎麼寫。需求後面再加幾句提示，要 AI 先跟你討論、不要直接動手：

# 需求
現在雙方只能在地面前後走、側移和出招，沒有辦法快速換到對手另一邊。
想要一招「越頂」：按住前進再按 Y，跳過對手落到他身後；離太遠就跳不過去，落在對手面前。這招不打人，只換位置。

# 開工前先跟我討論，不要直接寫程式
1. 先讀專案裡相關的程式與資料；能自己查到的事實，不要問我。
2. 把還沒決定的事一題一題列出來，每題附上你建議的答案；我回答「是」就代表採用建議。
3. 一輪只問現在就能回答的題目；我答完，再問被這些答案帶出來的下一輪。
4. 全部決定好、我確認之後，才整理成 SPEC。

這段提示的重點是分工：查事實是 AI 的事，做決定是你的事。AI 每題先給建議，你只要同意或改掉，討論就能很快收斂。

步驟 2｜討論

AI 讀過專案現有的程式後，把需求裡沒說清楚、或和現有規則衝突的地方一題一題問出來，設計者逐題決定。越頂一共討論了 16 題，下表挑五題。題目是依 SPEC 的決策整理的，不是原始對話紀錄。

AI 問的問題 為什麼要問 決定
跳躍的軌跡要用動畫帶動，還是程式控制？ 現有攻擊只要角色離地就會被取消，動畫的垂直移動也會被丟掉 程式控制：照固定拋物線放置角色，距離和高度由程式決定
不打人的招式，要不要給它一個假的傷害判定？ 現有規則要求每一招都要有 Hitbox 和 Damage 不給假的判定；改成允許三個欄位一起留空，叫做「無傷害招式」
跳的時候會不會撞到對手的身體？ 兩個角色的膠囊碰撞體會互相阻擋 離地期間暫時不擋對手；落地若重疊，推到重疊較少的一側
跳到一半被打中怎麼辦？ 空中被打的情況以前不存在 停止前進、自然落下，照常扣血並進入硬直
跳的時候畫面會不會亂轉？ 攝影機會一直追著兩人的連線轉 離地期間鎖住攝影機的角度，落地後再平順轉回

AI 每一輪會把題目編號、附上建議答案。你逐題回覆：同意就說「是」，不同意就直接寫你的決定。下面是一輪回覆的示意：

Q1 是，用程式控制軌跡。
Q2 是，不給假的傷害判定，改成允許三欄一起留空。
Q3 改：落地重疊時推到重疊較少的一側；那一側被牆擋住，就改推另一側。
Q4 是，空中被打就停止前進、自然落下。
Q5 是，離地期間鎖住攝影機角度。
其他沒問到的，請繼續問下一輪。

步驟 3｜產出 SPEC

討論完，AI 把結果整理成 SPEC。提示詞裡把第 8 週的開工順序寫進去：新增系統時，先定義資料與介面，再規劃 Init → Tick → End，最後接入遊戲流程。

討論的題目都決定了，請整理成 SPEC：
1. 依序寫：問題、解法、使用者故事、實作決策、驗收情境。
2. 使用者故事寫玩家看得到的行為，一條一件事。
3. 實作決策照這個順序寫，不要把所有邏輯塞進 Tick：
   - 資料與介面：要保存哪些狀態、初始值、對外與私有方法，誰擁有這些資料。
   - Init：開始時準備什麼、清掉什麼。
   - Tick：每一幀依時間推進什麼。
   - End：怎麼停止、清除狀態，讓下一次能重新開始。
   - 接入與測試：由誰、在什麼時機呼叫上面的方法，怎麼確認結果。
4. 驗收情境要能在遊戲裡重現，每一條編號。
5. 再把 SPEC 拆成工單：每張都要有做完就能展示的成果，並寫出要等哪張先做完。
先給我看，我確認後再存檔。

步驟 4｜實作 SPEC

AI 一次只做一張工單。開工前先讀 SPEC 和相關程式，做完一張、驗收通過就提交一次，再做下一張。

請照 SPEC 實作工單 03「離地軌跡與落地分開」：
1. 開工前先讀 SPEC、工單 03 和相關的程式，回覆你打算改哪些檔案、怎麼改。
2. 我確認後才開始改。
3. 只做工單 03 的範圍；發現 SPEC 沒寫到的情況，先停下來問我。
4. 做完回報改了什麼、怎麼驗收，等我確認後再提交。

拆單的順序有道理：先做「資料能不能表達這種招式」（01、02），再做「位置怎麼動」（03），最後才處理被打、畫面和 CPU 這些周邊情況（04～06）。每一步都在前一步驗收過的基礎上加東西，出問題時知道是哪一步壞的。

步驟 5｜驗收 SPEC

每張工單都要照 SPEC 的驗收情境實際跑過才算完成：

請驗收工單 03：
1. 逐條跑 SPEC 裡屬於工單 03 的驗收情境，能自動化的寫成測試，會動的在 PIE 實際跑。
2. 每一條回報：怎麼測、結果通過或失敗、證據在哪裡。
3. 失敗、跳過或沒辦法測的，照實寫出原因，不要寫成通過。
4. 再跑一次既有的回歸測試，確認舊功能沒有壞。

驗收包含下面幾件事：

  • 自動化測試：純規則用 Automation 測試，例如工單 01 加了無傷害招式的驗證案例。
  • PIE 實測：會動的部分寫成測試腳本，在 PIE 裡實際跑，例如工單 03 量起跳點、落點和兩人有沒有重疊。
  • 驗收紀錄：每次結果寫成驗收紀錄，失敗和沒測到的也要記。工單 06 跑了完整回歸，24 支中 23 支通過，沒過的那一支經查是越頂之前就存在的問題。
  • 程式審查：全部做完再審一次程式，審查時發現「越頂不該被別的招接進來」，補上檢查才收尾。

圖 4｜越頂從按鍵到落地，每個系統做了什麼？（泳道循序圖，箭頭下方是關鍵程式碼）

這張圖從上往下讀，每一欄是一個系統。四個關鍵點：

  1. 資料認得出不打人的招式：Source/TndaFighter/DataTable/TndaCommandReader.cpp 的 Prepare()，Hitbox 和 Hurtboxes 都空白時設 bNoDamage。
  2. 起招時抄下參數：Source/TndaFighter/Fighting/FightingCommandLink.cpp 的 FFightingAttackTiming::ReadMontage()，讀到 Airborne Arc 就把距離、高度和兩條曲線複製一份。跳到一半改資產，要到下一次出招才生效。
  3. 每一幀由程式放置位置：Source/TndaFighter/Fighting/FightingCharacter.cpp 的 Tick() 先呼叫 UpdateAirborneArc()。它在起跳時呼叫 BeginAirborneArc() 記下面向、關掉對手之間的阻擋；之後用 AirborneArcAt() 把進度換成走了幾公分、離地幾公分。軌跡方向是起跳那一幀的面向，不追蹤對手。
  4. 離地不再取消攻擊：同檔的 UpdateAttack() 原本只要角色離地就取消攻擊，現在多了 IsAirborneArcActive() 的例外，越頂自己造成的離地不算。

越不越得過，看距離

起跳時兩人中心的距離小於水平距離，才有機會越過對手。下表是備課時在 PIE 實測的結果，「站距」是起跳前兩人中心的距離：

水平距離 站距 越過了嗎
200 cm（本週值） 100 cm 越過
200 cm（本週值） 250 cm 沒越過，落回對手前方
300 cm 250 cm 越過
150 cm 100 cm 越過
150 cm 180 cm 沒越過

停一下，確認自己懂了： 把水平距離改成 300 cm 後，站距 100 cm 起跳，落點會在對手哪一邊、離起跳點大約多遠？

參考答案

落在對手的另一邊，離起跳點大約 300 cm。

  1. 站距 100 cm 小於水平距離 300 cm，軌跡會從對手上方通過，所以越得過。
  2. 軌跡沿起跳面向走完整段水平距離，落點離起跳點約 300 cm，也就是在對手身後約 200 cm。

備課時在 PIE 實測，落點離起跳點 299.9 cm。

# plan.md 格式
依序只用四個一級標題：「# 需求：功能名稱」「# 規格」「# 驗收目標」「# 現在開始」。
- 需求：一句「我想…」寫玩家看到的效果；需要時再一句指出要改的檔案或資料表。
- 規格：條列行為、規則、數值與邊界，一條一件事；寫出範圍外項目，不寫類別或函式名。
- 驗收目標：條列能在 PIE、Combat Debug 或 Output Log 判斷的結果，
  涵蓋正常操作、中斷、錯誤資料與受影響的舊功能。
- 現在開始：交代下一關要查什麼、提出什麼方案讓我確認，確認後整理 spec.md，等我確認才實作。
  新對話只貼這份 plan.md 也能接續。
# spec.md 格式

## 1. 目標與範圍

## 2. 現況與已確認規則

## 3. 實作設計
每套功能各開小節，完整展開以下五步：
1. 資料與介面：型別、初始值、單位、擁有者、公開／私有方法與輸入輸出。
   涉及表格時列 CSV、Row、執行期副本、Reader、驗證與舊資料相容方式。
2. Init：觸發條件、資料準備、清除舊狀態、無效輸入與重複啟動的處理。
3. Tick：更新時機、時間來源、狀態推進與停止條件；公式附符號、單位與小算例。
4. End：正常結束、中斷、停用與生命週期清理；哪些歸零、哪些保留、如何重啟。
5. 接入與手動確認：呼叫者、插入位置、先後順序、保留的既有行為與建置／資產更新順序。
每一步列檔案／資產、修改位置、內容、原因，以及學生應檢查的重點。
新名稱標示「預計新增」；不適用寫原因，事件驅動寫實際入口；必要時附偽碼。

每項依序寫：編號、確認目標、準備條件、操作步驟、預期畫面或 Log、結束後如何還原。
步驟寫清楚開哪個檔案或畫面、改動要看哪裡、遊戲內按什麼、觀察什麼。
涵蓋建置與啟動、異動內容檢查、正常功能、中斷與受影響的舊功能；先提供最小可操作案例。
## 5. 分階段工單
表格欄位：編號、範圍、相依工單、修改檔案／資產、可展示成果、手動驗證項目編號。
## 6. 未決事項
列問題與建議；存檔版必須寫「無」，還有未決事項就不存檔。
# 存檔與提交

寫進自己的 AGENTS.md

每次開新對話都重貼三段很花時間。Codex 這類 AI 代理開工時，會自動讀取專案裡的 AGENTS.md；把長期不變的規則寫進去，之後就不必每次重貼。教材專案沒有附根目錄的 AGENTS.md，這份由你自己寫、自己維護。

  1. 建立檔案：在 TndaFighter.uproject 同一層建立 AGENTS.md。Source/AGENTS.md 與 Source/TndaFighter/Fighting/AGENTS.md 是教材附的程式規則，保留原樣。
  2. 搬進每次都適用的規則：
    • 共用開場 1 的專案範圍、要先讀的文件、操作與資料入口。
    • 共用開場 2 的 unreal-mcp 位址、開工前確認與資產操作規則。
    • 共用提示詞的合作流程、plan.md 與 spec.md 格式、存檔提交、施工與驗證分工。
  3. 不要搬的句子：各段的「本輪回覆格式」，以及「本段先記住規則，不修改檔案」「本輪不修改功能」這類只管當下那一輪的句子。寫進 AGENTS.md 後每一輪都會生效，AI 會一直只回固定句子，或一直不動工。
  4. 改成你自己的版本：用自己的話整理，刪掉用不到的規則，補上實作中學到的事，例如常犯的錯、建置步驟。保持精簡；AI 每次都會讀這份檔案，越長越容易稀釋重點。
