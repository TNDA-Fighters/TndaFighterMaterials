TNDA Week 01 課前預習｜教師版

使用方式

本文件用來檢查學生能否正常使用開發環境，以及是否已從操作結果辨認 Third Person 四種玩法。環境安裝屬於課前條件，不占用兩組各 30 分鐘的實作時間。

教材與環境前置條件

  • Unreal Engine 5.8。
  • Visual Studio 2026，已安裝 Unreal C++ 開發所需工作負載與元件。
  • GitHub Desktop。
  • ThirdPersonTemplate 教材專案可編譯、可開啟，且包含以下關卡：
    • /Game/ThirdPerson/Lvl_ThirdPerson
    • /Game/Variant_Combat/Lvl_Combat
    • /Game/Variant_Platforming/Lvl_Platforming
    • /Game/Variant_SideScrolling/Lvl_SideScrolling

課前實作 1｜比較四種 Third Person 玩法（30 分鐘內）

給學生看的題目

使用 PIE 依序體驗 Lvl_ThirdPerson、Lvl_Combat、Lvl_Platforming 與 Lvl_SideScrolling。整理四種玩法在角色操作、鏡頭、關卡互動與遊戲目標上的差異，並為每個關卡留下一張能看出特色的執行畫面。

教學目的

讓學生先從玩家體驗辨認範本差異，知道 Variant 是可拆解與改造的專案起點，不是四套彼此無關的引擎功能。

完整操作

  1. 開啟 ThirdPersonTemplate，確認目前沒有編譯錯誤。
  2. 在 Content Browser 依序開啟四個關卡。
  3. 每次切換關卡後啟動 PIE，實際操作角色並觀察鏡頭、移動能力、場景互動與可見 UI。
  4. 每個關卡擷取一張能辨認特色的畫面。
  5. 整理比較表，最後選出較適合近戰遊戲原型的起點。

參考答案與教學基準

關卡 應辨認的核心差異
Lvl_ThirdPerson 標準第三人稱移動、跳躍、自由視角與基礎關卡。
Lvl_Combat 徒手攻擊、連段、AI 對手與場景內血條。
Lvl_Platforming 衝刺、牆跳與更強調精準移動的平台玩法。
Lvl_SideScrolling 固定鏡頭、平面移動限制、拾取物與橫向平台互動。

學生的文字不必和表格一致，但必須以實際操作觀察為依據。選擇近戰遊戲起點時，以 Combat 最直接；若學生選擇其他 Variant，只要能說明取捨，不直接判錯。

完成判斷與證據

  • 四個關卡都各有一張 PIE 畫面。
  • 比較表至少涵蓋操作、鏡頭、互動與目標中的三項。
  • 選型理由能對應到所選 Variant 的實際特色。

還原方式

本題只切換並執行關卡，不應修改資產。若誤存關卡變更，使用 GitHub Desktop 檢查差異，只還原本題造成的檔案變更。

常見問題

  • 找不到關卡：確認 Content Browser 沒有啟用只顯示特定資料夾或資產類型的篩選。
  • PIE 出現錯誤地圖：先確認目前開啟的關卡名稱，再按 Play。
  • 操作方式不同：以各關卡內建提示與實際反應為準，不要求四個 Variant 使用完全相同的輸入。

課前實作 2｜讓專案從 Combat 關卡開始（30 分鐘內）

給學生看的題目

把編輯器啟動時開啟的關卡，以及遊戲使用的預設關卡，都改成 Lvl_Combat。關閉並重新開啟專案，確認編輯器會直接進入 Combat 關卡，而且 PIE 可以正常操作角色。

教學目的

讓學生分清楚「目前開啟的關卡」與「專案預設關卡」，並熟悉會寫入專案設定的基本操作。

完整操作

  1. 開啟 Edit > Project Settings。
  2. 進入 Project > Maps & Modes。
  3. 將 Editor Startup Map 設為 /Game/Variant_Combat/Lvl_Combat。
  4. 將 Game Default Map 設為 /Game/Variant_Combat/Lvl_Combat。
  5. 關閉 Project Settings，確認設定已寫入 Config/DefaultEngine.ini。
  6. 關閉並重新開啟專案，確認目前關卡是 Lvl_Combat。
  7. 啟動 PIE，確認角色能移動並使用 Combat 玩法。

參考答案與教學基準

兩個欄位都應顯示 Lvl_Combat。重新開啟專案會驗證 Editor Startup Map；Game Default Map 則以設定頁或 DefaultEngine.ini 的值確認。單純在目前關卡按 Play，不足以單獨證明兩個欄位都已設定。

完成判斷與證據

  • 設定畫面同時顯示兩個 Lvl_Combat。
  • 重新啟動後目前關卡為 Lvl_Combat。
  • PIE 可正常控制 Combat 角色。

還原方式

課堂將沿用 Combat 關卡，因此學生可保留設定。若要回到教材原始狀態，將 Editor Startup Map 與 Game Default Map 都改回 /Game/ThirdPerson/Lvl_ThirdPerson。

常見問題

  • 只改了一個欄位：重新檢查 Maps & Modes 內的兩個 Map 欄位。
  • 重新開啟後仍是舊關卡：確認選到的是 Lvl_Combat 資產，而不是只在 Content Browser 選取它。
  • GitHub Desktop 出現 DefaultEngine.ini 變更：這是本題預期結果；應確認差異只包含兩個 Map 設定。

TNDA Week 01 課堂示範｜教師版

示範 1｜Gameplay Framework 與 Unity 對照（20 分鐘內）

示範目標

用 Lvl_Combat 說明 Unreal 如何把關卡規則、玩家控制與可控制角色拆開，並讓有 Unity 經驗的學生建立可用的責任對照。

備課前置

  • 開啟 ThirdPersonTemplate 的 Lvl_Combat。
  • 事先確認以下 Blueprint 可開啟：BP_CombatGameMode、BP_CombatPlayerController、BP_CombatCharacter。
  • 準備一個 PIE 視窗，能看見玩家角色與敵人。

建議節奏與操作

  1. 0～4 分鐘：從執行結果反推角色。 在 PIE 指出關卡開始後，誰決定生成什麼 Pawn、誰接收本機輸入、誰真正出現在世界中。
  2. 4～10 分鐘：沿資產關係說明。 從關卡使用的 GameMode 開始，依序打開 PlayerController 與 Character，說明 Possess 把控制者與 Pawn 接起來。
  3. 10～16 分鐘：補齊 Framework 責任。 說明 GameMode 只存在於權威端、GameState 保存整場可共享狀態、PlayerState 保存每位玩家的狀態。Week 01 先理解責任，不展開網路同步實作。
  4. 16～20 分鐘：與 Unity 對照。 使用下表逐項比較，最後回到 Lvl_Combat 的實際資產。

Unity 概念對照

這些對照只用來理解責任，不是類型、生命週期或網路模型的一對一映射。

Unreal 主要責任 Unity 中可近似聯想到的做法
GameMode 定義關卡或比賽規則、預設 Pawn 與 Controller 類別 場景啟動器、GameManager 或自訂規則服務的組合
PlayerController 代表玩家的控制端，接收輸入並 Possess Pawn PlayerInput 加上玩家控制腳本，但 Unity 沒有完全相同的內建角色
Pawn 可被 Controller Possess 的世界物件 可控制的 GameObject 加自訂控制元件
Character 具備 Capsule 與 Character Movement 的 Pawn 角色 GameObject、CharacterController 與移動腳本的組合
PlayerState 保存單一玩家、適合共享或同步的狀態 玩家資料元件或網路玩家狀態物件
GameState 保存整場遊戲的共享狀態 Match Manager 或網路化的場次狀態物件
Actor Component 把能力或資料組合到 Actor 上 Component／MonoBehaviour 的組合概念最接近

必講重點

  • PlayerController 與 Character 是兩個物件；「玩家」不等於角色 Blueprint。
  • Pawn 必須被 Possess 才能由對應 Controller 控制。
  • GameMode、GameState 與 PlayerState 的資料可見性及生命週期不同，不能全部塞進單一 Manager。
  • Unity 對照的用途是幫助定位責任，不是照名稱直接移植程式碼。

示範中常見狀況

  • World Settings 顯示的 GameMode 與 Project Settings 不同：說明關卡可用 GameMode Override 覆寫專案預設。
  • PIE 找不到 PlayerController：可用 World Outliner 切到 PIE 世界，或以 Blueprint 類別關係說明，不把時間花在 Debug 工具設定。

示範 2｜從按鍵走到 Input Action（20 分鐘內）

示範目標

讓學生看懂 按鍵 → Input Mapping Context → Input Action → 角色行為 的最小路徑，為課堂實作新增 U 鍵做準備。完整的 Enhanced Input 設計概念留到 Week 02。

備課前置

  • 開啟 /Game/Variant_Combat/Input/IMC_Combat。
  • 準備 /Game/Variant_Combat/Input/Actions/IA_ComboAttack 與 BP_CombatCharacter。
  • 確認原始設定中滑鼠左鍵會觸發 IA_ComboAttack。

建議節奏與操作

  1. 0～4 分鐘：先操作。 在 PIE 以滑鼠左鍵觸發攻擊，請學生先記住輸入結果。
  2. 4～9 分鐘：打開 IMC。 找到滑鼠左鍵對應的 IA_ComboAttack，說明 IMC 管理「目前情境可用哪些映射」。
  3. 9～14 分鐘：打開 IA。 說明 Input Action 表示玩家意圖，按鍵只是其中一種來源；簡短指出 Value Type、Trigger 與 Modifier 的位置。
  4. 14～18 分鐘：回到 Character。 顯示 Character 接收 IA 事件後才執行攻擊，建立資產與行為的分工。
  5. 18～20 分鐘：串起流程。 用口頭或白板畫出 Left Mouse Button → IMC_Combat → IA_ComboAttack → BP_CombatCharacter。

必講重點

  • 同一個 Input Action 可以有多個按鍵映射，因此不必複製攻擊邏輯。
  • IMC 管情境與映射，IA 表達意圖，Character 執行遊戲行為。
  • Modifier 改寫輸入值，Trigger 判斷何時成立；本週只辨認位置，不展開組合設計。
  • 新增第二個按鍵時要保留原本映射，才能讓兩種輸入都觸發同一功能。

示範中常見狀況

  • IA 名稱搜尋不到：先確認正在編輯的是 IMC_Combat，而不是 Project Settings 的舊式 Input 頁面。
  • PIE 沒有反應：先點一下遊戲 Viewport 取得鍵盤與滑鼠焦點。

課堂實作 1｜讓 U 鍵也能攻擊（15 分鐘內）

給學生看的題目

在不移除滑鼠左鍵的前提下，讓鍵盤 U 鍵也能觸發相同的連段攻擊。完成後分別使用滑鼠左鍵與 U 鍵測試，確認兩種輸入都會執行同一個功能。

教學目的

確認學生能修改既有 IMC 映射，並理解「增加輸入來源」不等於「複製一套攻擊邏輯」。

教材專案前置條件

  • 使用 ThirdPersonTemplate 的 Lvl_Combat。
  • /Game/Variant_Combat/Input/IMC_Combat 已有 Left Mouse Button → IA_ComboAttack。

參考操作

  1. 開啟 IMC_Combat。
  2. 找到 IA_ComboAttack 的既有滑鼠左鍵映射。
  3. 在同一個 Input Action 下新增一筆 Mapping。
  4. 將新 Mapping 的 Key 設為鍵盤 U，保留滑鼠左鍵那一筆。
  5. 儲存 IMC_Combat，進入 PIE。
  6. 分別按滑鼠左鍵與 U 鍵，確認兩者都觸發連段攻擊。

參考答案與基準

IMC_Combat 內應同時存在 Left Mouse Button → IA_ComboAttack 與 U → IA_ComboAttack。不需要在 Character 內新增第二套攻擊事件。

完成判斷與證據

  • IMC 畫面可同時看見兩筆映射。
  • PIE 中兩個按鍵都能觸發攻擊。
  • 學生能指出兩個按鍵最後共用的是 IA_ComboAttack。

還原方式

若要回到教材原始狀態，刪除 U 鍵那一筆 Mapping，保留滑鼠左鍵映射後儲存。

常見問題

  • 新增了另一個 IA：刪除多餘 IA，改在既有 IA_ComboAttack 下增加 Mapping。
  • U 鍵無反應：確認新 Mapping 的 Key 是鍵盤 U，且 PIE Viewport 已取得焦點。
  • 滑鼠左鍵失效：檢查是否誤把原本 Mapping 改成 U，而不是新增一筆。

課堂實作 2｜把移動速度調成兩倍（15 分鐘內）

給學生看的題目

把 Combat 操控角色的移動速度調成目前的兩倍。完成後進入 PIE，比較修改前後從同一位置走到同一目標所需的時間。

教學目的

讓學生從 Character 的元件設定找到移動參數，並以可重複的遊戲內比較判斷修改是否生效。

教材專案前置條件

  • /Game/Variant_Combat/Blueprints/BP_CombatCharacter 的 Character Movement 可正常使用。
  • 原始 Max Walk Speed 為 400 cm/s。

參考操作

  1. 開啟 BP_CombatCharacter。
  2. 在 Components 選取 Character Movement。
  3. 在 Details 搜尋 Max Walk Speed。
  4. 將數值由 400 改為 800。
  5. Compile、Save，進入 Lvl_Combat 的 PIE。
  6. 從同一個起點朝同一個目標移動，比較修改前後的時間或錄影。

參考答案與基準

目標值為 800 cm/s。這代表角色的最大步行速度設定為原本兩倍，不代表短距離實測時間一定精準減半；加速度、路線與計時誤差都會影響結果。

完成判斷與證據

  • BP_CombatCharacter 的 Max Walk Speed 顯示為 800。
  • Blueprint 編譯沒有錯誤。
  • PIE 中角色明顯比原始設定移動得快，且比較使用同一起點與目標。

還原方式

將 Max Walk Speed 改回 400，Compile 並 Save。

常見問題

  • 改到錯誤角色：確認資產是 BP_CombatCharacter，不是其他 Variant 的 Character。
  • 找不到欄位：先選取 Character Movement 元件，再搜尋完整欄位名稱。
  • 改完沒有差異：確認已 Compile，且 PIE 使用的是 Lvl_Combat 與正確 Character。
