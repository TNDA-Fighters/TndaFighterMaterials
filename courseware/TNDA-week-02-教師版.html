TNDA Week 02 課前預習｜教師版

教材發布前置檢查

本週所有操作都必須在學生收到的 TndaFighter 專案內完成。發布前確認：

  • /Game/Fighting/stage1 能直接執行。
  • docs/ 內已放入 FightingCameraActor 架構流程文件，並涵蓋角色生成、View Target、中點構圖、距離映射與最大角色距離限制。
  • docs/blueprints/ABP_Manny_Combat.md 與受阻移動流程文件可直接開啟。
  • PIE 期間可在 World Outliner 選到執行時產生的 FightingCameraActor，Details 可調整 Fighting Camera 類別下的屬性。

目前工作區尚未包含 FightingCameraActor 架構流程文件；在該文件放入教材專案前，本週課前實作 2 不具備完整教材條件。

課前實作 1｜畫出雙角色與攝影機的關係（30 分鐘內）

給學生看的題目

比較 stage1 在編輯狀態與 PIE 執行期間出現的物件，找出 PlayerController、1P、CPU Spawner、CPU 與 FightingCameraActor。畫一張架構圖，標示哪些物件原本就在關卡中、哪些在執行時產生，以及彼此的生成、控制與 View Target 關係。

教學目的

讓學生分清楚關卡 Actor、執行時生成物件、Possession 與 View Target，避免把「控制角色」和「目前攝影機」視為同一件事。

教材專案前置條件

  • stage1 編輯狀態可看到 PlayerStart 與 CPU_Spawner。
  • BP_FightingGameMode、BP_FightingPlayerController、BP_FightingPlayerCharacter、BP_FightingCpuSpawner 與 BP_FightingCpuCharacter 可開啟。

完整操作

  1. 開啟 stage1，在非 PIE 狀態記錄 World Outliner 的 PlayerStart 與 CPU_Spawner。
  2. 啟動 PIE，切換到 PIE 世界的 World Outliner，找出 PlayerController、1P、CPU 與 FightingCameraActor。
  3. 對照 Blueprint 類別與 C++ 流程，確認 1P、CPU 與攝影機各自從哪裡產生。
  4. 確認 PlayerController Possess 的 Pawn 是 1P，但 View Target 會切換到 FightingCameraActor。
  5. 用箭頭畫出生成、Possess、追蹤與 View Target 關係。

參考答案與教學基準

核心答案是：PlayerController Possess 1P，卻把 View Target 設為共用 FightingCameraActor。CPU 由關卡內的 CPU_Spawner 生成，不由玩家控制。

完成判斷與證據

  • 兩張 Outliner 畫面能辨認編輯狀態與 PIE 世界。
  • 架構圖包含指定的五個角色，且生成、Possess 與 View Target 箭頭方向正確。
  • 短答能清楚說明 Possessed Pawn 與 View Target 可以是不同物件。

還原方式

本題只觀察執行狀態與資產，不需修改專案。結束 PIE 即回到編輯世界。

常見問題

  • Outliner 看不到執行時角色：確認 PIE 已開始，並切到 PIE 對應的 World。
  • 把 CPU Spawner 當成 CPU：要求學生比較 Class 與出現時機；Spawner 是關卡 Actor，CPU 是執行時角色。
  • 找不到攝影機：FightingCameraActor 由 PlayerController 在執行時產生，非 PIE 狀態不會出現在關卡 Outliner。

課前實作 2｜調整雙人構圖範圍（30 分鐘內）

給學生看的題目

閱讀教材專案內的 FightingCameraActor 架構流程文件，找出會影響「1P 與 CPU 最遠能離多遠」及「兩人靠近時鏡頭能拉多近」的設定。各做一次調整並在 PIE 比較結果，記錄修改前後的數值與畫面；測試結束後恢復教材原始設定。

教學目的

讓學生從架構圖追到可調屬性，理解角色可分離範圍與 Camera Boom 距離雖然互相影響，但負責的是兩種不同限制。

教材專案前置條件

  • FightingCameraActor 架構流程文件已放入教材專案。
  • FightingCameraActor 使用目前原生預設值：MinCameraDistance=440、MaxCameraDistance=690、MinFighterDistance=110、MaxFighterDistance=570、DistanceInterpolationSpeed=5。
  • 學生可在 PIE Eject 後選取執行時的 FightingCameraActor。

完整操作

  1. 閱讀架構流程文件，先圈出角色距離限制與鏡頭距離映射兩條流程。
  2. 啟動 PIE，按 F8 Eject，在 PIE World Outliner 選取 FightingCameraActor。
  3. 記錄 Fighting Camera > Distance 內的原始值。
  4. 將 MaxFighterDistance 暫時提高到 900，並把 MaxCameraDistance 提高到 850，重新控制角色後測試雙方能否離得更遠且仍留在畫面中。
  5. 將 MinCameraDistance 暫時降低到 320，讓雙方靠近後觀察鏡頭是否拉得更近。
  6. 擷取原始值與修改值的近距離、遠距離畫面。
  7. 停止 PIE，重新執行一次，確認執行時修改已恢復。

參考答案與教學基準

  • MaxFighterDistance 同時是角色最大水平距離限制，以及距離映射的輸入上界。提高它後，1P 才能離 CPU 更遠。
  • MinCameraDistance 是雙方靠近時 Camera Boom 使用的最短距離。降低它會讓近距離構圖更貼近角色。
  • MaxCameraDistance 只決定鏡頭最多拉多遠，不會單獨放寬角色移動上限。
  • 上述 900、850、320 是便於觀察的課堂參考值，不是遊戲平衡定案。

完成判斷與證據

  • 紀錄同時包含角色距離設定與鏡頭距離設定。
  • 前後畫面能辨認角色最遠距離或近距離構圖的差異。
  • 學生能說出提高 MaxCameraDistance 不等於角色就能站得更遠。

還原方式

本題在 PIE 執行時修改 Actor Instance，停止 PIE 即會還原。重新開始 PIE 後，再確認五個原始值已恢復。

常見問題

  • Details 沒有 Fighting Camera 類別：確認選到的是 PIE 世界裡的 FightingCameraActor，不是 CameraComponent 或編輯世界 Actor。
  • 數值改了卻不能控制角色：按 F8 重新 Possess，或重新開始 PIE。
  • 拉遠後角色仍被限制：先確認 MaxFighterDistance 也有提高，而不是只改 MaxCameraDistance。
  • 停止 PIE 後數值消失：這是本題的預期還原方式，不要嘗試把執行時 Actor 存回關卡。

示範 1｜從雙角色生成到 ABP 動畫（20 分鐘內）

示範目標

把 stage1 的角色生成、Possession、共用攝影機與 locomotion 動畫串成一條可閱讀的流程，讓學生知道每個系統各自負責哪一段。

備課前置

  • stage1 可正常出現 1P、CPU 與雙人構圖。
  • FightingCameraActor 架構流程文件已放入教材專案。
  • docs/blueprints/ABP_Manny_Combat.md 與 docs/blueprints/changes/2026-09-01-blocked-movement-locomotion.md 可開啟。
  • 預先開啟 BP_FightingCpuSpawner、BP_FightingPlayerController 與 ABP_Manny_Combat，避免遠端示範等待載入。

建議節奏與操作

  1. 0～4 分鐘：雙角色進場。 在 stage1 指出 PlayerStart 與 CPU_Spawner。進入 PIE 後說明 1P 由 PlayerController Possess，CPU 由 Spawner 的 Spawn Capsule Transform 生成，初始朝向 1P 出生位置。
  2. 4～9 分鐘：View Target 與共同構圖。 說明 PlayerController 建立 FightingCameraActor；攝影機取得 1P 與最近的 CPU 後呼叫 SetViewTarget，因此控制對象仍是 1P，畫面來源則是共用攝影機。
  3. 9～14 分鐘：鏡頭如何跟著兩人。 指出攝影機每幀計算雙方中點、以 16:9 保留構圖，並依水平距離在最小與最大鏡頭距離之間映射。角色換邊時選擇離目前 Yaw 較近的取景側，避免鏡頭翻轉 180 度。
  4. 14～20 分鐘：ABP 快速導覽。 開啟 ABP_Manny_Combat，依序指出 EventGraph 讀角色與移動資料、Variables 保存 Ground Speed 等資料、AnimGraph 產生 Pose、State Machine 切換狀態、BlendSpace 依速度與方向混合動畫。

ABP 必講重點

  • EventGraph 整理資料，AnimGraph 輸出 Pose，兩者不是同一種流程圖。
  • State Machine 決定 Idle、移動或跳躍等狀態，BlendSpace 負責同一狀態內的連續混合。
  • ABP_Manny_Combat 在角色仍有輸入但實際位移受阻時，會提供動畫用的速度替代值；它不會改寫真實移動速度。
  • 受阻 locomotion 的完整節點流程留在教材專案文件，示範只帶學生知道如何閱讀，不在 20 分鐘內逐節點重做。

示範中常見狀況

  • CPU 尚未出現時畫面短暫等待：說明攝影機會等待有效對手，再完成 View Target 切換。
  • 學生把 Camera Boom 距離當成角色距離：回到流程圖分開指出 MaxFighterDistance 與 Camera Distance。
  • ABP 圖太大：只聚焦 EventGraph 的 movement data 與 AnimGraph 的 Locomotion，不在本次展開攻擊 Montage。

示範 2｜Enhanced Input 的設計概念與 Unity 對照（20 分鐘內）

示範目標

用 TndaFighter 的移動輸入解說 Input Action、Input Mapping Context、Modifier、Trigger、Value Type 與執行時 Context 管理，並與 Unity Input System 做責任對照。

備課前置

  • 開啟 Epic Games：Enhanced Input。
  • 備妥 Unity Input System 1.17：Actions 與 Interactions，用來核對 InputAction、InputActionMap、started、performed 與 canceled 的用途。
  • 準備 /Game/Fighting/Input/IMC_Combat、/Game/Fighting/Input/Actions/IA_Move、BP_FightingPlayerController 與 BP_FightingPlayerCharacter。
  • 確認 WASD 能在 PIE 驅動 1P 移動。

建議節奏與操作

  1. 0～4 分鐘：從玩家意圖開始。 IA_Move 表達「移動」，不是 W、A、S、D 中任何一顆按鍵；Value Type 決定這個意圖傳遞 Bool、Axis1D、Axis2D 或 Axis3D。
  2. 4～8 分鐘：查看 IMC。 在 IMC_Combat 指出實體按鍵如何組成 IA_Move 的 Axis2D 值，以及同一 IA 可以有多個映射。
  3. 8～12 分鐘：分清 Modifier 與 Trigger。 Modifier 先轉換輸入值；Trigger 再判斷何時產生 Started、Ongoing、Triggered、Completed 或 Canceled 等事件。
  4. 12～16 分鐘：執行時掛載。 顯示 PlayerController 從 Local Player 取得 Enhanced Input Local Player Subsystem，再加入預設 IMC；Character 將 IA_Move 的 Triggered 事件綁到 Move()。
  5. 16～20 分鐘：與 Unity Input System 對照。 用下表比較責任，並串回 WASD → IMC_Combat → IA_Move → FInputActionValue → Move()。

Unity Input System 概念對照

以下是用途上的近似比較，不代表資產格式、事件時機或生命週期完全相同。

Unreal Enhanced Input 主要責任 Unity Input System 可近似聯想到的概念
Input Action 定義玩家意圖與 Value Type InputAction
Input Mapping Context 將按鍵映射分組，並可在執行時加入、移除及排序 InputActionMap 加上啟用／停用策略
Modifier 先改寫輸入值，例如 Negate、Swizzle、Dead Zone Processor 或 Composite 內的值轉換
Trigger 判斷輸入在何種條件與時機成立 Interaction；實際 phase 語意並非一對一
Enhanced Input Local Player Subsystem 管理本機玩家目前啟用的 IMC 與優先權 PlayerInput、InputUser 或程式碼管理 Action Map 的組合
IA Event／C++ BindAction 把輸入事件接到遊戲行為 started、performed、canceled callback 或 Input System event

必講重點

  • IA 與 IMC 是資料資產；玩家控制與角色行為不該全部塞在 IMC。
  • Context 優先權適合處理 Gameplay、Menu 等模式切換，不必為每個模式重寫按鍵事件。
  • Modifier 處理「值變成什麼」，Trigger 處理「何時算成立」。
  • UE 的 Triggered 與 Unity 的 performed 常可用來理解主要行為事件，但不能假設觸發條件完全一致。

示範中常見狀況

  • IMC 已設定但事件沒進 Character：依序檢查 Context 是否加入、IA 是否綁定、Pawn 是否由正確 PlayerController Possess。
  • Axis2D 方向錯誤：回到每個 WASD Mapping 的 Modifier，檢查 Negate 與 Swizzle，而不是在 Character 內硬改按鍵。

TNDA Week 02 課堂實作｜教師版

課堂實作 1｜移動 CPU 出生位置（15 分鐘內）

給學生看的題目

先記錄 stage1 內 CPU_Spawner 的 Transform，再把它移到另一個位置。進入 PIE，比較 CPU 的出生位置與初始朝向；完成紀錄後，把 CPU_Spawner 還原到原始 Transform。

教學目的

讓學生直接驗證 Spawner、Spawn Capsule 與生成角色的關係，並觀察 CPU 初始朝向不是單純照抄 Spawner 的旋轉。

教材專案前置條件

  • stage1 內有 CPU_Spawner 與 PlayerStart。
  • CPU_Spawner 原始 Transform 為 Location (1800, 1926, 210)、Rotation (0, 0, 0)、Scale (1, 1, 1)。
  • CPU Spawn Capsule 相對 Spawner 向上 90 cm。

參考操作

  1. 非 PIE 狀態選取 CPU_Spawner，擷取 Details 的 Transform。
  2. 保持 Y、Z、Rotation 與 Scale 不變，把 Location X 由 1800 改成 2050。
  3. 進入 PIE，觀察 CPU 是否從新的 Spawn Capsule 位置出現，以及初始是否仍朝向 PlayerStart。
  4. 擷取移動後的 Spawner、CPU 出生位置與初始朝向。
  5. 停止 PIE，把 Location X 改回 1800，再核對完整 Transform。

參考答案與基準

  • CPU 使用 Spawn Capsule 的世界 Transform 生成，因此 X 位置會跟著 Spawner 改變，生成高度仍包含 Capsule 的相對 Z 偏移。
  • CPU 生成後會重新朝向 PlayerStart，不是直接沿用 CPU_Spawner 或 Spawn Direction 的旋轉。
  • X=2050 只是方便在現有場地觀察的參考值，不是正式關卡配置。

完成判斷與證據

  • 有原始 Transform 與修改值紀錄。
  • PIE 畫面能看出 CPU 出生位置跟著 Spawner 改變。
  • 學生能指出 CPU 初始面向 PlayerStart。
  • 結束時 Transform 已完整還原。

還原方式

將 CPU_Spawner 設回 Location (1800, 1926, 210)、Rotation (0, 0, 0)、Scale (1, 1, 1)，儲存 stage1。再用 GitHub Desktop 確認沒有留下本題的關卡變更。

常見問題

  • 移動 CPU 而不是 Spawner：停止 PIE，回到編輯世界選取 CPU_Spawner。
  • CPU 沒在 Spawner 原點：提醒學生 CPU 取用的是 Spawn Capsule Transform，Capsule 有相對高度。
  • CPU 面向和 Spawner 箭頭不同：這是預期行為；生成流程會讓 CPU 朝向 PlayerStart。

課堂實作 2｜比較鏡頭距離插值速度（15 分鐘內）

給學生看的題目

在 stage1 的 PIE 執行期間，把 FightingCameraActor 的 DistanceInterpolationSpeed 分別調成一個低值與一個高值。讓 1P 與 CPU 反覆靠近、遠離，比較鏡頭縮放的跟隨速度；記錄兩種設定的畫面或短片，結束後恢復原始狀態。

教學目的

讓學生直接感受插值速度只改變「追上目標值的快慢」，不改變最小與最大鏡頭距離。

教材專案前置條件

  • PIE 期間可選取 FightingCameraActor。
  • DistanceInterpolationSpeed 的原始值為 5。
  • 1P 可在攝影機移動基準下靠近或遠離 CPU。

參考操作

  1. 啟動 PIE，按 F8 Eject，在 PIE World Outliner 選取 FightingCameraActor。
  2. 將 DistanceInterpolationSpeed 改為 0.5，重新控制 1P，快速改變雙方距離並錄下鏡頭反應。
  3. 再次 Eject，將數值改為 20，用相近的移動路線重新測試。
  4. 比較鏡頭到達新距離的速度，以及最終近、遠構圖是否改變。
  5. 停止 PIE，重新執行並確認數值回到 5。

參考答案與基準

  • 0.5：鏡頭較慢追上目標距離，縮放有明顯延遲。
  • 20：鏡頭很快靠近目標距離，反應更直接。
  • 兩者最後仍受同一組 MinCameraDistance 與 MaxCameraDistance 限制；插值速度不會放大距離範圍。

完成判斷與證據

  • 低值與高值各有一段畫面或清楚的觀察紀錄。
  • 兩次測試使用相近的角色移動方式。
  • 學生能區分插值速度與鏡頭距離範圍。

還原方式

停止 PIE 即可捨棄執行時修改。重新開始 PIE 後，確認 DistanceInterpolationSpeed=5。

常見問題

  • 修改後無法移動：按 F8 重新 Possess，或重新開始 PIE。
  • 高低值看不出差異：讓角色先靠近 CPU，再快速走到接近最大距離的位置，並固定相近測試路線。
  • 最終畫面距離不同：檢查是否同時誤改了 MinCameraDistance 或 MaxCameraDistance。
