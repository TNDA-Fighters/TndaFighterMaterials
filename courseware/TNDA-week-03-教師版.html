TNDA Week 03 課前預習｜教師版

教材發布前置檢查

本週重點是閱讀與觀察既有實作，不要求學生建立相對方向或自動面向功能。發布前確認：

  • Week 03 教材專案已完成 Opponent Reference、戰鬥軸、4／6 相對方向、最後有效方向與平順自動面向。
  • docs/ 已包含「換邊與自動面向」架構流程文件，內容與實際類別、變數及執行順序一致。
  • FacingInterpolationSpeed、面向 Debug 資料與換邊測試方式已存在專案內，不需上課時補發。
  • docs/為何 1P 與 CPU 不會疊在一起呢.md 與 docs/blueprints/ABP_Manny_Combat.md 可直接開啟。

目前工作區尚未具備 Week 03 的自動面向實作、FacingInterpolationSpeed 與對應架構文件；補齊並驗證前，本週課前實作 2 與後續課堂內容不能直接使用現況授課。

課前實作 1｜讓 1P 與 CPU 可以重疊（30 分鐘內）

給學生看的題目

先記錄 1P 與 CPU 的根 Capsule 碰撞設定，以及兩者接觸時的畫面。只調整教材專案中既有的碰撞設定，嘗試讓 1P 能進入並穿過 CPU 的位置。留下修改前後的設定與 PIE 畫面，完成後恢復原始設定。

教學目的

讓學生從可觀察的阻擋行為追到根 Capsule 的 Collision Response，確認角色模型與防重疊規則不是同一層。

教材專案前置條件

  • BP_FightingPlayerCharacter 與 BP_FightingCpuCharacter 的根元件都是 CollisionCylinder。
  • 兩個 Capsule 的 Object Type 都是 Pawn，Collision Enabled 都是 Query and Physics，對 Pawn 的 Response 都是 Block。
  • 兩個 Capsule 的 Radius 都是 35 cm，並已開啟 Generate Overlap Events。

完整操作

  1. 分別開啟 BP_FightingPlayerCharacter 與 BP_FightingCpuCharacter，選取根 CollisionCylinder，記錄 Collision Presets、Object Type、Collision Enabled 與 Pawn Response。
  2. 在原始狀態進入 PIE，讓 1P 持續朝 CPU 移動，擷取兩個 Capsule 被阻擋的畫面。需要時使用 show collision 顯示碰撞範圍。
  3. 停止 PIE，開啟 BP_FightingCpuCharacter，把根 Capsule 的 Pawn Response 由 Block 改為 Overlap，其他 Channel 不變。
  4. Compile、Save，再進入 PIE，讓 1P 穿過 CPU 並擷取畫面。
  5. 停止 PIE，將 CPU 根 Capsule 的 Pawn Response 改回 Block，Compile、Save，再次確認兩者會互相阻擋。

參考答案與教學基準

原始阻擋來自兩名 ACharacter 的根 Capsule：Object Type 是 Pawn，雙方對 Pawn 都是 Block。把其中一方改為 Overlap 後，兩個 Capsule 可以互相進入，且 Generate Overlap Events 開啟時可保留 Overlap 事件條件。Skeletal Mesh 不是本題阻擋角色移動的元件。

完成判斷與證據

  • 原始設定紀錄包含兩個角色的根 Capsule。
  • 修改紀錄能指出 CPU 的 Pawn: Block → Overlap。
  • PIE 畫面能辨認修改前受阻、修改後可穿過。
  • 最後已恢復 Pawn: Block，並再次確認阻擋行為。

還原方式

在 BP_FightingCpuCharacter > CollisionCylinder 將 Collision Presets 保持原本的 Custom，並把 Pawn Response 設回 Block。Compile、Save 後，以 GitHub Desktop 確認沒有留下本題變更。

常見問題

  • 改 Skeletal Mesh 後仍不能穿過：角色移動阻擋由根 Capsule 處理，應檢查 CollisionCylinder。
  • 使用 Ignore 也能穿過：可以達成穿越，但不會產生 Overlap 事件；本題參考操作使用 Overlap 方便比較責任差異。
  • 改回 Block 後仍能穿過：確認修改的是 CPU 根 Capsule，並已 Compile；也要檢查 PIE 是否仍在使用修改前的執行實例。

課前實作 2｜把換邊流程分成 Gameplay 與 ABP（30 分鐘內）

給學生看的題目

閱讀教材專案內的「換邊與自動面向」架構流程文件，把 Opponent Reference、戰鬥軸、4／6 相對方向、目標面向、旋轉插值與 ABP Pose 分到 Gameplay 與 Animation Blueprint 兩個責任區。畫一張雙泳道流程圖，標出資料從角色位置一路到畫面姿勢的方向。

教學目的

讓學生把角色規則與動畫呈現拆開閱讀，知道 ABP 應消費結果並產生 Pose，而不是決定對手、輸入語意或 Actor 世界旋轉。

教材專案前置條件

  • 「換邊與自動面向」文件能連回教材專案內的實際類別、屬性與 ABP 變數。
  • Week 03 版本已實作最後有效方向備援，重疊時不會反覆切換方向。

完整操作

  1. 先沿文件找出 Opponent Reference 的建立位置與更新時機。
  2. 從 1P、CPU 世界位置追到水平戰鬥軸，記錄距離過近時採用的備援資料。
  3. 追蹤實體移動方向如何和戰鬥軸比較，並在輸入事件產生時保存 4／6 語意。
  4. 從同一份戰鬥軸追到目標面向與 Actor Rotation Interpolation。
  5. 最後開啟 ABP_Manny_Combat，確認 ABP 讀取移動與旋轉結果，再由 AnimGraph、State Machine 與 BlendSpace 產生 Pose。
  6. 把以上流程畫成 Gameplay 與 Animation Blueprint 兩條泳道。

參考答案與教學基準

概念 主要責任區 原因
Opponent Reference Gameplay 代表目前互動對象，會影響規則與控制。
戰鬥軸 Gameplay 由雙方位置推導，供方向語意與面向共同使用。
4／6 相對方向 Gameplay 是輸入與指令語意，必須在事件產生時確定。
目標面向 Gameplay 決定 Actor 在世界中的朝向。
旋轉插值 Gameplay／Character Movement 實際更新 Actor Rotation，而不是只改骨架 Pose。
ABP Pose Animation Blueprint 讀取角色結果，選擇並混合畫面中的骨架姿勢。

ABP 可以依 Actor Rotation、Velocity 或相對方向挑選動畫，但不應成為決定對手或改寫 4／6 指令的唯一來源。

完成判斷與證據

  • 六個指定概念都有放入泳道，且資料箭頭方向完整。
  • Gameplay 流程先產生角色狀態，ABP 再讀取狀態形成 Pose。
  • 學生能指出 ABP 不應負責的至少一項遊戲規則。

還原方式

本題只閱讀資產與文件，不需修改專案。

常見問題

  • 把「轉身動畫」和「Actor 旋轉」畫成同一件事：前者是 Pose，後者會改變角色在世界中的方向。
  • 先在 ABP 判定 4／6：提醒學生方向事件要保存當下語意，後續換邊不能回頭改寫已記錄輸入。
  • 重疊時重新算出不穩定方向：應沿用最後有效戰鬥軸或最後有效面向。

TNDA Week 03 課堂示範｜教師版

教材發布前置檢查

以下示範以完成版 Week 03 教材專案為前提。專案必須已包含相對方向、自動面向、最後有效方向備援、FacingInterpolationSpeed 與 ABP Debug 資料；老師不在遠端課堂臨時加入節點或程式碼。目前工作區尚未具備這些內容，發布前需先完成並依實際名稱校對本文件。

示範 1｜從角色碰撞到 4／6 相對方向（20 分鐘內）

示範目標

說明角色為何不會重疊，以及同一個實體方向鍵如何依 1P 與 CPU 的相對位置轉成格鬥遊戲的前進 6 或後退 4。

備課前置

  • 開啟 stage1、BP_FightingPlayerCharacter、BP_FightingCpuCharacter 與「換邊與自動面向」流程文件。
  • PIE 可顯示碰撞，並可查看教材專案提供的戰鬥軸、相對方向與最後有效方向 Debug 資料。

建議節奏與操作

  1. 0～4 分鐘：先看碰撞。 在 PIE 顯示 Collision，讓 1P 靠近 CPU。指出 Character Movement 移動根 Capsule，雙方 Pawn → Block 形成 Blocking Hit；Skeletal Mesh 不負責阻止兩人穿越。
  2. 4～8 分鐘：建立 Opponent Vector。 用 OpponentLocation - SelfLocation 得到指向對手的向量，移除 Z 後正規化成水平戰鬥軸。
  3. 8～13 分鐘：判定 4／6。 將本次移動方向與「指向對手」的戰鬥軸比較。同向代表朝對手前進，可記為 6；反向代表遠離對手，可記為 4。強調語意在方向事件產生時保存。
  4. 13～17 分鐘：交換左右位置。 讓 1P 位於 CPU 的另一側，使用同一組實體按鍵，觀察戰鬥軸反轉後 4／6 語意同步反轉。
  5. 17～20 分鐘：處理重疊例外。 雙方距離太近時，新方向不可靠，沿用最後有效戰鬥軸與最後有效面向，避免方向及旋轉在每幀跳動。

必講重點

  • Capsule Collision 解決「能不能穿過」，戰鬥軸解決「前後方向怎麼解讀」，兩者是不同規則。
  • 4／6 是相對於對手的輸入語意，不是固定綁死螢幕左鍵或右鍵。
  • 戰鬥軸與自動面向應共用同一份對手資料，避免角色面向和指令方向互相矛盾。
  • 距離接近零時不要正規化不穩定向量；使用最後有效值是本週的保底策略。

示範中常見狀況

  • Debug 顯示的 4／6 沒有反轉：先確認 1P 確實換到 CPU 另一側，再檢查 Opponent Reference 是否有效。
  • 重疊時方向快速跳動：代表近零距離仍在產生新戰鬥軸，應回到最後有效值的分支。

示範 2｜換邊後如何平順轉身，ABP 又負責什麼（20 分鐘內）

示範目標

沿著「目標面向 → Actor 旋轉插值 → ABP 讀取結果 → Pose」說明換邊後的平順轉身，清楚劃分 Gameplay 與 Animation Blueprint 的責任。

備課前置

  • Week 03 教材專案已公開 FacingInterpolationSpeed，並有可重複的換邊測試方式。
  • ABP_Manny_Combat 的 Debug Filter 可選到 1P 與 CPU 的執行實例。
  • 面向或方向 Debug 變數名稱已寫入教材專案流程文件。

建議節奏與操作

  1. 0～5 分鐘：算出目標面向。 從角色到對手的水平向量取得 Desired Yaw；雙方各自使用指向對方的方向，所以會互相面對。
  2. 5～10 分鐘：加入 Rotation Interpolation。 比較直接設定 Desired Rotation 與逐幀插值。指出 Delta Seconds 保持不同幀率下的時間尺度，FacingInterpolationSpeed 控制追上目標的快慢。
  3. 10～14 分鐘：說明 Rotation Ownership。 Gameplay／Character Movement 負責 Actor 在世界中的旋轉；ABP 不應偷偷把遊戲方向規則藏在 Pose 裡。
  4. 14～18 分鐘：使用 ABP Debug Filter。 選取 1P 實例，觀察 EventGraph 取得的移動與旋轉資料，再看 AnimGraph、State Machine 與 BlendSpace 如何依結果產生待機、前進、後退或轉身中的 Pose。
  5. 18～20 分鐘：完成換邊。 讓 1P 穿越 CPU，指出戰鬥軸、Desired Yaw、Actor Rotation 與 ABP Pose 更新的先後關係。

必講重點

  • Desired Yaw 是目標，Actor Rotation 是目前結果；插值讓兩者不必在同一幀相等。
  • FacingInterpolationSpeed 改變轉身速度，不改變最終應面向哪裡。
  • ABP 負責把目前角色狀態表現成骨架 Pose；Gameplay 邏輯仍是相對方向與世界旋轉的權威來源。
  • ABP Debug Filter 看的是某一個執行中 Anim Instance，必須選對 1P 或 CPU。

示範中常見狀況

  • 角色世界旋轉已改，動畫看起來仍像滑行：檢查 ABP 使用的 Direction、Ground Speed 與目前 State／BlendSpace，而不是再疊一套 Actor 旋轉。
  • Debug Filter 沒有實例：先保持 PIE 執行，再回到 ABP 編輯器選取對應角色。
  • 高插值速度看起來像瞬間翻面：換成較低值重做同一路徑，讓學生看出差異。

TNDA Week 03 課堂實作｜教師版

教材發布前置檢查

兩組實作只操作 Week 03 教材專案內已存在的 Actor、屬性與 Debug 資料。發布版需先完成並驗證相對方向、自動面向、FacingInterpolationSpeed、ABP Debug 變數與可穿越 CPU 的換邊測試方式。目前工作區尚缺這些內容，未補齊前不可把下列題目直接交給學生操作。

課堂實作 1｜交換 1P 與 CPU 的起始左右位置（15 分鐘內）

給學生看的題目

只調整 stage1 內 PlayerStart 與 CPU_Spawner 的位置，讓 1P 開場時站在 CPU 的右側。進入 PIE，觀察雙方初始面向、A／D 的相對前進與後退，以及格鬥攝影機的構圖；完成紀錄後還原兩個 Actor 的 Transform。

教學目的

讓學生不改程式碼就能驗證相對方向與自動面向不是綁死在固定出生側，並同時檢查攝影機換邊策略。

教材專案前置條件

  • Week 03 的 4／6 相對方向與自動面向已啟用。
  • 原始位置：PlayerStart=(1800, 1663, 302)、CPU_Spawner=(1800, 1926, 210)。
  • PlayerStart 原始 Rotation 約為 (Pitch 0, Yaw 90, Roll 0)；CPU_Spawner 原始 Rotation 為 (0, 0, 0)。

參考操作

  1. 在非 PIE 狀態擷取 PlayerStart 與 CPU_Spawner 的完整 Transform。
  2. 只交換兩者的 Y 位置：PlayerStart.Y=1926、CPU_Spawner.Y=1663，保留各自的 X、Z、Rotation 與 Scale。
  3. 進入 PIE，確認畫面中 1P 開場位於 CPU 右側，雙方會朝向彼此。
  4. 分別按 A、D，記錄哪一個是朝向對手的前進 6，哪一個是遠離對手的後退 4。
  5. 觀察格鬥攝影機是否仍把雙方放在畫面內，且沒有翻轉 180 度。
  6. 停止 PIE，還原兩個 Actor 的完整 Transform。

參考答案與基準

  • 1P 位於 CPU 右側時，應面向畫面左側的 CPU。
  • 朝畫面左側、接近 CPU 的 A 應解讀為前進 6；朝畫面右側、遠離 CPU 的 D 應解讀為後退 4。
  • 攝影機可以更新共同中點與取景，但不應因開場左右交換而翻到場景另一側。

完成判斷與證據

  • PIE 畫面可辨認 1P 位於 CPU 右側且雙方面向正確。
  • A、D 的 4／6 紀錄符合相對於對手的方向。
  • 畫面仍維持雙人構圖，沒有 180 度鏡頭翻轉。
  • 兩個 Actor 的 Transform 已還原。

還原方式

  • PlayerStart：Location (1800, 1663, 302)、Rotation 約 (0, 90, 0)、Scale (1, 1, 1)。
  • CPU_Spawner：Location (1800, 1926, 210)、Rotation (0, 0, 0)、Scale (1, 1, 1)。
  • 儲存 stage1 後，用 GitHub Desktop 確認沒有留下本題的關卡差異。

常見問題

  • 交換整個 Transform 後角色高度錯誤：本題只交換 Y，Z 與 Rotation 必須留在各自 Actor。
  • 1P 站到右側卻背對 CPU：確認 Week 03 自動面向已執行，且 Opponent Reference 有效。
  • 4／6 沒有反轉：確認測試紀錄採用的是相對方向 Debug 值，不是直接把 A、D 當成 4、6。

課堂實作 2｜比較平順轉身的插值速度（15 分鐘內）

給學生看的題目

使用教材專案既有的換邊測試方式，把 FacingInterpolationSpeed 分別調成一個低值與一個高值。讓 1P 穿過 CPU 完成換邊，並在 ABP_Manny_Combat 的 Debug Filter 觀察角色資料與 Pose。比較兩種設定的轉身速度，完成後恢復教材原始設定。

教學目的

讓學生把可調參數、Actor Rotation 與 ABP Pose 放在同一次觀察裡，確認插值速度影響轉身過程，不改變最終面向規則。

教材專案前置條件

  • FacingInterpolationSpeed 已公開在學生可直接調整的位置，且架構文件寫明所在資產與原始值。
  • 教材專案已有可穿越 CPU 的換邊測試方式；若採 Collision Response，操作位置與還原值必須寫入專案文件。
  • ABP_Manny_Combat 的 Debug Filter 可選到 1P 執行實例，並能觀察 Direction、面向 Debug 資料與目前 Pose。

參考操作

  1. 先記錄 FacingInterpolationSpeed 原始值，啟用教材專案既有的換邊測試方式。
  2. 在 1P 與 CPU 使用的面向設定中，將 FacingInterpolationSpeed 暫時設為 1。
  3. 進入 PIE，開啟 ABP_Manny_Combat，把 Debug Filter 指向 1P。讓 1P 穿過 CPU，錄下 Actor 轉身與 ABP Pose 的變化。
  4. 將相同設定改為 20，用相近路線再完成一次換邊並錄影。
  5. 比較低值與高值到達目標面向所需的時間；確認換邊後最終仍朝向 CPU。
  6. 停止 PIE，恢復 FacingInterpolationSpeed 原始值與換邊測試設定。

參考答案與基準

  • 1：Actor 較慢追上 Desired Yaw，轉身過程較長。
  • 20：Actor 很快追上 Desired Yaw，視覺上更接近立即轉身。
  • 兩種設定的最終面向都應是朝向 CPU；如果最終方向不同，問題不在插值速度。
  • ABP 的 Pose 應跟著執行中角色的移動與旋轉資料更新，不能只看 Blueprint 預覽角色。

1 與 20 是方便在 15 分鐘內觀察的參考值。教材發布時仍須在流程文件記錄專案實際原始值與屬性位置。

完成判斷與證據

  • 低值與高值各有一次完整換邊紀錄。
  • Debug Filter 明確選到 1P 執行實例。
  • 學生能分辨 Desired Yaw、Actor Rotation 與 ABP Pose。
  • 結束時插值速度與換邊測試設定已還原。

還原方式

將 FacingInterpolationSpeed 改回開始前記錄的原始值。若換邊測試使用 CPU Capsule 的 Pawn Response，將它改回 Block，Compile、Save，並以 GitHub Desktop 檢查沒有留下本題變更。

常見問題

  • Debug Filter 只看到預覽角色：保持 PIE 執行，重新選取 1P 的 Anim Instance。
